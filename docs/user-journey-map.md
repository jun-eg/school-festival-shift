# ユーザージャーニーマップ — 学祭シフト作成

> 『ユーザが特定のゴールを達成するまでの一連の体験』を可視化する。

アイデア出しフレームワーク 3 ステップの **1 つ目**。出力（改善機会リスト）が HMW の入力になる。

## 凡例：情報の出典

マップ内の各項目には出典を付ける。**想像で埋めた部分と裏が取れた部分を区別する**ため。

| 記号 | 意味 |
| --- | --- |
| ◎ | 裏が取れている（2026-09-12 の本人ヒアリングで確認） |
| △ | 想像で埋めた（未検証。インタビューで確かめる） |

## ペルソナ

| 項目 | 内容 |
| --- | --- |
| **名前** | 佐藤 みなみ（仮名）△ |
| **属性・所属** | 大学 2 年。サークルの模擬店でシフト担当を任されている一般メンバー ◎。実行委員ではなく、専任でもない △ |
| **ゴール** | 4 日間の模擬店を、各コマに必要な人数が埋まった状態で回しきる ◎ |
| **前提知識・スキル** | Google フォーム／スプレッドシートは「作れるし触れる」レベル ◎。関数やマクロで自動化する知識はない △ |
| **置かれている制約** | ・メンバーは 20〜30 人、期間は 4 日間 ◎<br>・**自分もシフトに入る当事者**であり、作る側と入る側を兼ねる ◎<br>・確定後の欠席・交代が当日も含めて頻繁に起きる ◎<br>・シフト作成は授業・バイトの合間の作業で、まとまった時間が取れない △<br>・メンバーへの強制力がなく、催促は「お願い」ベース △ |

### 立場を 1 人に絞った理由

「シフトを作る人」と「シフトに入る人」で体験が分かれるが、**このペルソナは両方を兼ねている**（本人もシフトを出す）◎。
マップの視点は **「作る人」としての体験**に固定し、「入る人」としての体験は
*作る人が自分の希望を後回しにする* という形でのみ登場させる。両方を並列に書くと改善機会がぼやけるため。

## 解像度が荒い部分（インタビューで聞く）

△ を付けた箇所が対象。**この節がそのまま Interview List**（聞きたいことの溜め場）として機能する。

聞きに行く前に `interview-questions` skill（`/interview-questions`）を呼び、この節を入力として
相手 1 人分のインタビューガイドを `docs/interviews/` に出す。
聞き方は `.claude/skills/interview-questions/references/interview.md` に従い、
**意見ではなく直近の実際の行動**を聞く。

### 1. 背景・状況
- シフト担当はどう決まったか。何人でやっているか（1 人か、複数人か）
- 過去に同じ作業をしたことがあるか。前年の資料は引き継がれているか

### 2. 枠の設計（ACTION 1）
- 1 日を何コマに割っているか。コマの長さは何時間か
- 1 コマあたり何人必要か。その人数はどうやって決めたか
- 役割（調理・接客・レジ）の区別はあるか。「この人でないと困る」枠はあるか

### 3. フォームと告知（ACTION 2〜4）
- フォームの項目は具体的に何か。自由記述はどう使われているか
- 告知は何回流すか。締切はいつに設定し、実際に守られるか
- 未提出者はだいたい何人くらい出るか。どうやって特定しているか
- 催促は誰がするか。どのくらい気を遣うか

### 4. 整理と割り当て（ACTION 5〜6）
- 「人力で整理する」とは具体的に何をしているか（並べ替え／コピペ／別シート作成）
- 整理から割り当て完了まで、実際に何時間かかったか。何日に分けてやったか
- 割り当てのとき、何を優先して決めているか（希望優先／公平性／経験者配置）
- 「公平」の基準は何か（合計コマ数／不人気枠の数／本人の希望充足率）
- 埋まらなかったコマは実際にあったか。どう埋めたか

### 5. 自分のシフト（ACTION 7）
- 自分の希望は実際に通っているか。他メンバーと比べてどうか
- 「作る側なので我慢した」経験は直近であったか

### 6. 変更対応（ACTION 9〜10）
- 確定後の変更は 4 日間で何件くらい起きたか
- 変更の連絡はどこに来るか（グループ／DM／口頭）
- 代わりの人はどうやって探したか。何人に声をかけたか
- 当日の欠員はどう埋めたか。記録は残っているか
- 変更後の表はどう共有したか。古い表を見ている人はいたか

### 7. まとめ
- この一連の作業で、一番大変だったのはどこか
- 理想の状態はどんな状態か
- 来年も同じやり方でやるとしたら、何が一番不安か

## 改善機会リスト

HMW（次工程）の入力。**解決策ではなく「機会」**として書いている。

### A. 希望収集まわり
- 未提出者を特定するのに毎回の突き合わせが必要で、催促のたびにコストがかかっている
- 催促が人間関係のコストを伴い、担当者 1 人が心理的に負担している
- 告知が LINE のタイムラインに埋もれ、未提出者に届き続けない
- 「最低○コマ」などの制約が依頼文でしか表現されておらず、入力時点で担保されない
- 自由記述の条件（バイト・授業）が構造化されず、担当者の解釈に依存している

### B. データ整理まわり
- 回答の生データと、割り当てに使える形の間に人力の変換工程が挟まっている
- 同じ整理作業が、回答が追加・修正されるたびに最初からやり直しになる
- 表記ゆれ・重複回答の掃除が毎回発生している

### C. 割り当てまわり
- 割り当ての制約（希望・必要人数・公平性・経験者配置）がすべて担当者の頭の中にあり、引き継げない
- 一箇所の変更が全体に波及し、やり直しのコストが大きい
- 公平に割り振れているかを確かめる手段が目視しかない
- 埋まらないコマの存在に気づくのが、組み終わった後になりやすい
- 枠の設計（コマ割り・必要人数）の根拠が記録されず、翌年に引き継がれない

### D. 共有・確認まわり
- 各自が自分の出番を把握したかを確認する手段がない
- 表全体を配る形式のため、個人が自分の出番を探す手間が残る
- 最新版がどれかが定まらず、古い表が参照され続ける

### E. 変更対応まわり（頻度が高く、影響が大きい）
- 変更が頻繁に起きる前提なのに、作り直しの手順が初回作成と同じ重さで発生する
- 代われる人を探す作業が担当者 1 人に集中している
- 当日の欠員が記録されないまま、担当者の即興対応で吸収されている
- 当日の変更が翌日以降のシフトに反映されず、同じ穴が繰り返される
- 誰が実際に働いたかの記録が残らない

### F. 担当者自身の立場
- 担当者の負担が作業量だけでなく、割り当ての不利としても積み上がっている
- 担当者自身の希望が、他メンバーと同じ土俵で扱われていない
