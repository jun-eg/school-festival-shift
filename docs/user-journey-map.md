# ユーザージャーニーマップ — 学祭シフト作成

> 『ユーザが特定のゴールを達成するまでの一連の体験』を可視化する。

アイデア出しフレームワーク 3 ステップの **1 つ目**。出力（改善機会リスト）が HMW の入力になる。

## 凡例：情報の出典

マップ内の各項目には出典を付ける。**想像で埋めた部分と裏が取れた部分を区別する**ため。

| 記号 | 意味 |
| --- | --- |
| ◎ | 裏が取れている（2026-09-13 の**担当経験者**インタビューで確認） |
| ◎入 | 裏が取れている（2026-09-13 の**シフトに入る側**インタビューで確認。現在 1 人のみ） |
| ○ | 伝聞・本人の推測（直接は観測していないが、証言としては出ている） |
| △ | 未検証（想像のまま。まだ誰にも確かめられていない） |

◎ と ◎入 を分けているのは、**作る側 1 人の証言と入る側の証言が混ざると、どちらの視点の裏付けなのか分からなくなる**ため。

### 作る側の証言を一般化するときの注意

**証言者は技術力が高い側の外れ値**である ◎。担当は**毎年 1 人が持ち回りで、幹部のこともメンバーのこともある** ◎ ため、
年によって担当者のスキルは大きく変わる。証言者は Google フォームに正規表現バリデーションを設定し、
スプレッドシートと紐づけ、スクリプトでデータを整備した ◎ が、**例年はそこまでやらない** ◎。
実際、前々年度は手でエクセルに転記していた ○。

さらに証言者は、シフト表を JSON で管理して **Vercel に確認サイトを自作** している ◎。
これも例年のやり方ではない ◎（引き継がれたやり方は LINE ノートに画像を貼るだけ ◎）。

→ 証言者の年に「軽かった」工程が、**例年も軽いとは限らない**。該当箇所には注記を入れてある。
→ 逆に、証言者が自作したもの（フォームのバリデーション／整備スクリプト／確認サイト）は
　 **どれも翌年に渡らない** ◎。「すでに試したこと」の節に、効いたもの・効かなかったものを整理してある。

### 入る側 1 人目（風蔵）を一般化するときの注意

**風蔵も外れ値側である。** 去年の学祭当時は幹部で、調理可だったため、

- 希望時間は「**幹部なのでほぼ全部**」で出しており ◎入、**予定を見比べて希望を絞る作業をしていない**
- シフト量を**他人と比べていない** ◎入（「幹部でずっといたので何とも」）

つまり**当時の立場が「どうせ大学に居る」側で、制約が薄く、比較もしない層**の証言である。
しかも作る側の証言者と**同学年・当時同じ幹部・どちらも調理可**で、属性がほぼ完全に重なっている。
issue #13 が散らそうとした軸（非調理／1・2 年／締切後提出／事後申告）は**まだ 1 つも埋まっていない**。

→ この 1 人で「入る側はこうだ」と決めない。**否定に見えるものは「縮小」までに留める。**

| 項目 | 内容 |

| **属性・所属** | 大学 3 年。サークルの模擬店でシフト作成を任された 1 人 ◎。実行委員ではない ◎ |

| **置かれている制約** | ・メンバーは 20〜30 人、期間は 4 日間（11/1〜11/4）◎<br>・**担当は毎年入れ替わる** ◎。押し付け、または幹部の持ち回りで決まる ◎<br>・**引き継がれるのは前年のシフト表 1 枚と、LINE の短い説明だけ** ◎<br>・**自分もシフトに入る当事者** ◎。証言者は調理と準備／片付けも兼任 ◎<br>・**学祭運営委員会の外部ルールに縛られる** ◎（下記）<br>・**無報酬** ◎<br>・確定後の欠席・交代が起きる ◎（4 日間で 5 件以下 ◎） |

### 立場を 1 人に絞った理由

「シフトを作る人」と「シフトに入る人」で体験が分かれるが、**このペルソナは両方を兼ねている** ◎。
マップの視点は **「作る人」としての体験**に固定する。

> **当初の想定は否定された。** 「作る側なので自分の希望を後回しにする」という体験は**無かった** ◎。
> 入る時間が多かったのは事実だが、理由は「幹部でどうせ大学に居るから」であり、シフト作成担当だからではない ◎。
> 担当者の負担は**割り当ての不利ではなく、無報酬の作業量そのもの**に出ている ◎。

## 外部制約：学祭運営委員会のルール

**当初のマップにはこの層が丸ごと無かった。** 割り当ての自由度を最も強く縛っているのがここ ◎。

| ルール | 内容 | 担当者に降りてくるタイミング |
| --- | --- | --- |
| **検便** | 事前に検便を提出し、委員会の許可を得た人だけが調理に入れる ◎ | **調理担当者名簿**としてフォーム作成**前**に配布される ◎ |
| **調理責任者** | 各調理枠に 3・4 年生を 1 人以上、調理責任者として置く ◎ | 同上（口頭・前年度担当者経由）◎ |
| **クリーンパトロール** | 委員会が指定した時間に、指定された人数を出す ◎ | **フォーム作成の後**に提示される ◎ |

## 証言された「理想の状態」

インタビューで**そのまま語られた**理想のフロー ◎。HMW と Design Doc の User Story の一次情報になる。

```
LINE にアンケート URL を貼る
  ↓
「シフト作成」ボタンを押す
  ↓
仮完成
  ↓
ちまちま手で少し修正（5〜15 分）
  ↓
完成
  ↓
LINE に流す
  ↓
修正依頼が来る
  ↓
手で修正（5〜15 分）
  ↓
LINE のノートを差し替える
```

読み取れること:

- **全自動は求められていない。** 「仮完成 → 手で微修正」が前提に入っている ◎
- 許容できる手作業は **5〜15 分**。現状の **3〜6 時間**との差が、解くべき距離 ◎
- 修正ループ（流す → 依頼が来る → 直す）も**同じ 5〜15 分**で回ることが期待されている ◎
- 出入口は **LINE** のまま ◎。置き換え対象は**割り当ての中身だけ**
  - これは「すでに試したこと」とも整合する。**LINE の外に出した確認サイトは使われなかった** ◎
- 修正の反映が「LINE のノートを差し替える」で終わっている ◎。現状の commit → push → PR → merge（10 分）はこの理想に含まれていない

## 確定した改善機会リスト

HMW（次工程）の入力。**解決策ではなく「機会」**として書いている。

### 確定（◎：インタビューで裏が取れた）

**最優先 — 割り当て**

1. 割り当てが全工程で唯一かつ最大のボトルネックになっている（3〜6 時間／3 日がかり／やり直し 20 回規模）
2. 「検便 × 学年（3・4 年）× 時間が合う」の 3 条件で調理系の候補が枯れ、**公平性を犠牲にしてでも同じ人を入れている**
3. 準備・片付けの割り当てルール（午前に仕事→準備／午後に仕事→片付け／両方ある人は片方／どちらも無い人は入れない／複数日で準備が同じ人に偏らないようにする）が複雑で、担当者の頭の中にしかない
4. 「公平」の基準（準備の回数・シフト回数・合計時間）が担当者の頭の中にあり、確かめる手段が目視しかない
5. 粗い単位で集めた希望を 30 分枠に割り直す変換が、担当者の頭の中でしか行われていない
6. 集めたのに使われない希望（「一緒に組めたら嬉しい友達」）がある。しかも入る側 1 人目は**そこに何も書いていない** ◎入 → 作る側も使わず、出す側も書いていない項目が残っている
7. 修正のたびに、初回と同じ制約チェック（検便・学年・時間）を手でやり直している
8. 割り当ての実体は **JSON の手編集**であり、支援は「表として見える」ところまでしかない。制約チェックも偏りの計算も人間に残っている
9. **見える化だけでは時間は縮まなかった**（JSON ＋ リアルタイム表示を作っても 3〜6 時間のまま）

**共有・確認**

10. LINE ノートに**画像と URL を並べると、画像が選ばれる**。見やすさのために作った確認サイトが使われなかった。入る側 1 人目も**画像を拡大して自分の名前を探していた** ◎入（画像を選んだ理由は未取得 △）
11. フォームにログインを付けていないため、**提出した本人の手元に希望の控えが残らない**（ただし入る側 1 人目は控えが無くて困っておらず、確認画面も使っていない ◎入 → **需要の広さは要検証**）

13. 生データ（スプレッドシート）をそのまま共有する道は、重複行とスマホ非対応で塞がっている
14. 1 件の変更を反映するのに commit / push / PR / merge が必要で、1 回 10 分かかる

**引き継ぎ**

15. 担当が毎年入れ替わるのに、渡るのは**前年のシフト表 1 枚と LINE の一文**だけ
16. 作り込んだもの（フォームのバリデーション・整備スクリプト・JSON・確認サイト）が**翌年に一切残らない**（「整ったデータの集まるフォームは引き継げない」）

**順序・タイミング**

21. 日ごと・年度ごとに営業時刻が変わるため、前年の成果物を再利用できない
22. 未提出者を特定しないまま割り当てが始まり、後から申告（締切後提出 5 人・流した後の指摘 1〜2 人）が来て組み直しになる

**担当者の立場**

23. 担当者が無報酬で、模擬店の他の役割（調理・準備・片付け）と兼任している

    **非調理／1・2 年／締切を過ぎて出した人（5 人）／事後申告した人（1〜2 人）は未着手**
  - フォームの入力しやすさ。バリデーションを厳しくした年の入力体験 ○（証言者の推測どまり）。
    1 人目からは詰まった箇所が出てこなかった ◎入 が、**当時幹部・スマホ・締切直前の 1 例のみ**
  - 画像で配られたシフト表から、自分の出番を見つける手間 → **拡大して探している** ◎入。
    ただし**なぜ画像で見たのか**（画像で困っていないのか／URL を開くのが面倒なだけか）は**未取得** △
  - 希望確認画面が**なぜ好評だったのか**（控えが無くて困っていたのか、単に珍しかったのか）。
    **1 人目は使っていない** ◎入 ため、理由はまだ取れていない
  - **全員分の希望が見えることの何が嫌だったのか**。1 人目は画面自体を使っておらず未取得
  - 希望がどのくらい通ったと感じているか。公平だと感じているか → 1 人目は**他人と比べていない** ◎入（当時幹部で「ずっと大学に居た」ため）。比較する層には未確認
  - 変更を申し出るときの言い出しにくさ → 「**言いづらいと思う**」◎入。ただし 1 人目は希望違いを経験しておらず、**実際に言えなかった人**には未確認
- **技術力の低い年の担当者の実態**
  - データ整理を手作業でやる場合、実際どのくらいかかるのか
  - フォーム作成のどこで詰まるのか
- **他サークル／他年度の担当者**の進め方（この学祭で共通の課題なのか、このサークル固有なのか）
- 催促の心理的コスト（**この証言者は催促していないため未観測**。催促する年の担当者には別の負担があるかもしれない）
- 未提出のまま組んだことが、入る側にどう受け取られているか
