# ユーザージャーニーマップ — シフトを**作る側**

> 『ユーザが特定のゴールを達成するまでの一連の体験』を可視化する。

アイデア出しフレームワーク 3 ステップの **1 つ目**。出力（改善機会リスト）が HMW の入力になる。

**立場ごとに 1 本**（issue #29）。もう 1 本は [入る側.md](入る側.md)。

## 凡例：情報の出典

マップ内の各項目には出典を付ける。**想像で埋めた部分と裏が取れた部分を区別する**ため。

| 記号 | 意味 |
| --- | --- |
| ◎ | 裏が取れている（2026-09-13 の**担当経験者**インタビューで確認） |
| ○ | 伝聞・本人の推測（直接は観測していないが、証言としては出ている） |
| △ | 未検証（想像のまま。まだ誰にも確かめられていない） |

**◎ のうち、記憶ではなく一次記録（提出記録のタイムスタンプなど）で確認したものには `（記録）` を添える。**
**記憶と記録が食い違ったときは記録を採る。**

**このマップの ◎ は、すべて作る側の証言を指す。** 立場を区別する枝分かれ記号（旧 `◎入`）は使わない。
枝分かれ記号が要る状態は、**マップに別の立場が混ざっているサイン**である。

入る側から持ち込んだ事実には記号を付けず、`→ 入る側:` と書いて [入る側.md](入る側.md) を指す。
**入る側の体験そのもの（提出のだるさ・出番の探し方・申し出のしにくさなど）は、このマップには置かない。**
ここに置くのは、**入る側の観測が作る側のタスクや改善機会に効いてくる部分**だけである。

**(n/m) は付けていない。** この立場について聞けたのは **1 人**なので、◎ はすべて (1/1) にしかならない。
1 人の証言でマップ全体が立っていることは、下の「一般化するときの注意」で担保する。

### 証言を一般化するときの注意

**証言者は技術力が高い側の外れ値**である ◎。担当は**毎年 1 人が持ち回りで、幹部のこともメンバーのこともある** ◎ ため、
年によって担当者のスキルは大きく変わる。証言者は Google フォームに正規表現バリデーションを設定し、
スプレッドシートと紐づけ、スクリプトでデータを整備した ◎ が、**例年はそこまでやらない** ◎。
実際、前々年度は手でエクセルに転記していた ○。

さらに証言者は、シフト表を JSON で管理して **Vercel に確認サイトを自作** している ◎。
これも例年のやり方ではない ◎（引き継がれたやり方は LINE ノートに画像を貼るだけ ◎）。

→ 証言者の年に「軽かった」工程が、**例年も軽いとは限らない**。該当箇所には注記を入れてある。
→ 逆に、証言者が自作したもの（フォームのバリデーション／整備スクリプト／確認サイト）は
　 **どれも翌年に渡らない** ◎。「すでに試したこと」の節に、効いたもの・効かなかったものを整理してある。

### このマップが扱う立場

**視点は「シフトを作る人」としての体験に固定する。**

このペルソナは**シフトに入る当事者でもある** ◎ が、**入る側としての体験は [入る側.md](入る側.md) に置く**。
1 本のマップに 2 つの立場を混ぜると、どちらの視点の裏付けなのか分からなくなるため（issue #29）。

> **当初の想定は否定された。** 「作る側なので自分の希望を後回しにする」という体験は**無かった** ◎。
> 入る時間が多かったのは事実だが、理由は「幹部でどうせ大学に居るから」であり、シフト作成担当だからではない ◎。
> 担当者の負担は**割り当ての不利ではなく、無報酬の作業量そのもの**に出ている ◎。

## 証言された「理想の状態」

インタビューで**そのまま語られた**理想のフロー ◎。HMW と Design Doc の User Story の一次情報になる。

```
LINE にアンケート URL を貼る
  ↓
「シフト作成」ボタンを押す
  ↓
仮完成
  ↓
ちまちま手で少し修正（5〜15 分）
  ↓
完成
  ↓
LINE に流す
  ↓
修正依頼が来る
  ↓
手で修正（5〜15 分）
  ↓
LINE のノートを差し替える
```

読み取れること:

- **全自動は求められていない。** 「仮完成 → 手で微修正」が前提に入っている ◎
- 許容できる手作業は **5〜15 分**。現状の **3〜6 時間**との差が、解くべき距離 ◎
- 修正ループ（流す → 依頼が来る → 直す）も**同じ 5〜15 分**で回ることが期待されている ◎
- 出入口は **LINE** のまま ◎。置き換え対象は**割り当ての中身だけ**
  - これは「すでに試したこと」とも整合する。**LINE の外に出した確認サイトは（作る側の受け取りでは）使われなかった** ◎
- 修正の反映が「LINE のノートを差し替える」で終わっている ◎。現状の commit → push → PR → merge（10 分）はこの理想に含まれていない

## 改善機会リスト

HMW（次工程）の入力。**解決策ではなく「機会」**として書いている。

**HMW は [入る側.md](入る側.md) の改善機会リストと合わせて 1 つの候補プールとして見る**（統合リストは作らない。issue #29）。

### 確定（◎：インタビューで裏が取れた）

**最優先 — 割り当て**

1. 割り当てが全工程で唯一かつ最大のボトルネックになっている（3〜6 時間／3 日がかり／やり直し 20 回規模）
2. 「検便 × 学年（3・4 年）× 時間が合う」の 3 条件で調理系の候補が枯れ、**公平性を犠牲にしてでも同じ人を入れている**
3. 準備・片付けの割り当てルール（午前に仕事→準備／午後に仕事→片付け／両方ある人は片方／どちらも無い人は入れない／複数日で準備が同じ人に偏らないようにする）が複雑で、担当者の頭の中にしかない
4. 「公平」の基準（準備の回数・シフト回数・合計時間）が担当者の頭の中にあり、確かめる手段が目視しかない。
   　→ 入る側: **割り当ての量そのものには不公平感が出ておらず、体感の重さはシフト表に載らない仕事で決まっている**（[入る側.md](入る側.md) 改善機会 14）。
   　**非調理の 1 人は「量が少ない」と気づいているが「ちょうどよかったです」** ◎（issue #42）→ **量の差は実在するが、不満にはなっていない**
   　→ **シフト時間を均す精度を上げても公平感には届かない**。基準をどこに置くかの問題
5. 粗い単位で集めた希望を 30 分枠に割り直す変換が、担当者の頭の中でしか行われていない
6. 集めたのに使われない希望（「一緒に組めたら嬉しい友達」）がある。
   　→ 入る側: **「書けば優遇される」と期待して書いている人がいる**（[入る側.md](入る側.md) 改善機会 2）→ **捨てられていることを出す側は知らない**。
   　**この欄は学籍番号を書くよう指定していた** ◎（issue #50 で確認）。**指定どおりと分かるのは 1/5 だけ**である。
   　**学籍番号 1/5**（5 人目）・**個人名 1/5**（3 人目）・**役職「サー長の先輩」1/5**（4 人目。**属性だが一意に辿れる**）・**「同期の女」1/5**（**辿れない**）・**空欄 1/5**。
   　→ **問題は「辿れない形が混じる」ことではなく、指定が守られていないことの方が多数である** ◎ **(4/5)**。
   　→ **それでも辿れる形は 3/5**（学籍番号・個人名・役職）なので、**「集まっている形では使えない」は依然 1/5 にとどまる**。
   　→ **そして、一意にするコストは入る側に出る** ◎ (1/5)。**指定を守った 1 人は「友達の学籍番号確認が時間かかった」と、そこで止まっている**（同 3・ACTION 4）。
   　**指定を厳しくすれば辿れる形は増えるが、そのぶん入る側が止まる**
7. 修正のたびに、初回と同じ制約チェック（検便・学年・時間）を手でやり直している
8. 割り当ての実体は **JSON の手編集**であり、支援は「表として見える」ところまでしかない。制約チェックも偏りの計算も人間に残っている
9. **見える化だけでは時間は縮まなかった**（JSON ＋ リアルタイム表示を作っても 3〜6 時間のまま）

**共有・確認**

10. LINE ノートに画像と URL を並べたときに、作る側は「**サイトは使われなかった**」と受け取っている ◎。
　　→ 入る側: **実際には割れており、サイトを使った人がいる**（[入る側.md](入る側.md) 改善機会 7）→ **使った人がいたことが担当者に届いていない**
11. フォームにログインを付けていないため、**提出した本人の手元に希望の控えが残らない** ◎（事実）。
　　ただし**「困った」と言った人は入る側 5 人ともいない** ◎ (5/5)（→ [入る側.md](入る側.md) 改善機会 5）。
　　根拠だった「好評」も**本人の感覚** ○ だった。**最も需要が出そうな層（希望を絞って出した人）でも「特に困らなかった」** ◎。
　　**ただし 5 人目で読み替えが必要になった** ◎ (1/5。issue #50) — **この人は見返したくなり、希望確認画面で実際に確認できている**。
　　→ **「需要が無い」のか「画面があったので満たされていた」のかが区別できていない**。
　　**確認しようとする行為は 2/5 で起きており、うち 1 人は画面で解決している** →
　　**「控えを目的に何かを作らない」は保つが、「いまある画面が控えとして効いているか」は別に見る**
12. **全員分が見えることには反応が出ている** ◎。複数人が「**全員分見れちゃうんだ**」と作る側に直接言っている。
　　**反応の中身が取れた** ◎ (1/1。issue #50)。**そう言った 1 人＝入る側 5 人目**に当たれ、
　　「**誰と組みたいか番号が見えた**」と答えている → **反応の対象は希望時間ではなく友達欄**である。
　　**こちらから「友達欄」という言葉は出していない**ので、**誘導ではない**。
　　**是非は「困らないけど、気まずい」** ◎ ＝ **拒否感でも単なる驚きでもない第 3 の答え**。
　　→ **対処は「自分の分だけ表示」ではなく「友達欄だけ隠す」で足りる** ◎。
　　**全員分が見える形そのものは、シフト表側では役に立っている**（→ [入る側.md](入る側.md) 改善機会 17）。
　　→ **ただし優先度は高くない**。**本人が「困らない」と言っている** ◎ —
　　**「嫌がられているから隠す」ではなく「隠しても失うものが無いから隠す」**。
　　**なお「番号」は学籍番号である** ◎ — **フォームが友達欄に学籍番号を指定していた**（→ ACTION 4）ので、
　　**誰と組みたいかが学籍番号で名指しされた形で全員に見えていた**。
　　**残る空白**: **画面そのものの良し悪し** △（**聞いたが回答が無かった**）と、
　　**画面の存在をどうやって知ったのか** △（**入る側 4 人目は存在自体を知らなかった** ◎ (1/5)）
13. 生データ（スプレッドシート）をそのまま共有する道は、重複行とスマホ非対応で塞がっている
14. 1 件の変更を反映するのに commit / push / PR / merge が必要で、1 回 10 分かかる。
　　→ 入る側: **当日も表を見る人がいる**（[入る側.md](入る側.md) 改善機会 8）→ **差し替えは当日分まで届く必要がある**

**引き継ぎ**

15. 担当が毎年入れ替わるのに、渡るのは**前年のシフト表 1 枚と LINE の一文**だけ
16. 作り込んだもの（フォームのバリデーション・整備スクリプト・JSON・確認サイト）が**翌年に一切残らない**（「整ったデータの集まるフォームは引き継げない」）
17. 各工程の重さが、**その年の担当者の技術力だけで決まってしまう**
18. 必要人数の根拠が「去年と同じ」しかなく、妥当性の検証も翌年への引き渡しもできない
19. 委員会のルール（検便・学年・クリーンパトロール）が文書化されず人伝いに渡っている

**順序・タイミング**

20. クリーンパトロールの枠が**フォーム作成後**に確定するため、枠設計が後から崩れる
21. 日ごと・年度ごとに営業時刻が変わるため、前年の成果物を再利用できない
22. 未提出者を特定しないまま割り当てが始まり、後から申告（**締切後の提出記録 6 人分** ◎（記録）＝ **締切に間に合わなかった 5 人 ＋ 締切内提出者の出し直し 1 人** ◎（記録）・流した後の指摘 **記録で 1 人** ◎（記録。**作る側の記憶では 1〜2 人**。**出し直しの 1 人と同一** ◎（記録。issue #48）））が来て組み直しになる。
    **ただしタイムスタンプは残っている** ◎（記録）→ **誰がいつ出したかは特定できる**

**担当者の立場**

23. 担当者が無報酬で、模擬店の他の役割（調理・準備・片付け）と兼任している

**当日運用（入る側の目撃から作る側のタスクに効いてくるもの）**

> この 2 つは**入る側が見た事実**だが、**手を入れられるのは作る側の枠設計と割り当て**なので、ここに置く。

　　**しかも記録の側からも確定した** ◎（記録）: **その 2 回目の提出は 2025/10/27 3:11:57** で、**シフト表の配布（10/27 深夜）より前**である →
