アイデア出しフレームワーク 3 ステップの **1 つ目**。出力（改善機会リスト）が HMW の入力になる。

この 1 本は「シフトを作る側」の体験だけを扱う。もう 1 本は [入る側.md](入る側.md)。

### 証言を一般化するときの注意

**証言者は技術力が高い側の外れ値である** ◎。担当は毎年 1 人が持ち回りで、幹部のこともメンバーのこともある ◎ ため、
年によって担当者のスキルは大きく変わる。証言者は Google フォームに正規表現バリデーションを設定し、
スプレッドシートと紐づけ、スクリプトでデータを整備し、シフト表を JSON で管理して Vercel に確認サイトを自作した ◎ が、
例年はそこまでやらない ◎（引き継がれたやり方は LINE ノートに画像を貼るだけ ◎）。前々年度は手でエクセルに転記していた ○。

→ 証言者の年に「軽かった」工程が、例年も軽いとは限らない。該当箇所には注記を入れてある。
→ 逆に、証言者が自作したものはどれも翌年に渡らない ◎。「すでに試したこと」に整理してある。

**この立場の ◎ も動く。** 1 人しかいない立場なので、証言が唯一の根拠になっている項目が多い。
実際、2026-09-13 の証言は 2 回動いている（→「更新ログ」）。
→ **入る側から返ってきた答えを、作る側に当て直す往復が要る。**
これまでの 2 回はどちらも副産物として出てきたのであって、狙って取ったものではない。

**当たれていない層が 2 つある** △。

| 当たれていない層 | 何が取れないままか |
| --- | --- |
| 技術力の低い年の担当者 | データ整理を手作業でやる場合の所要時間。フォーム作成のどこで詰まるか |
| 他年度・他サークルの担当者 | この学祭で共通の課題なのか、このサークル固有なのか |

**本人に聞けば埋まる空白も残っている** △: 催促した数人が誰で何人か／催促しても出さなかった人がいたか／
催促そのものが負担だったか。どれも記録には残らない。

聞けなかった範囲は △ のまま残してある。「未検証（△）」節に一覧がある。

## すでに試したこと

証言者は例年のやり方に不満を持ち、いくつか自作している ◎。
**何が効いて何が効かなかったか**がはっきりしているので、Design Doc の Alternatives Considered の一次情報になる。

| 試したこと | 目的 | 効いたか ◎ | 翌年に渡ったか ◎ |
| --- | --- | --- | --- |
| フォーム項目への正規表現バリデーション | 集まるデータを綺麗にする | 整備工程は軽くなった。友達欄に残った値は全件が学籍番号 ◎（記録 24/24）。ただし「弾かれた人はいない → 入る側 (5/5)」は自己申告で、記録と食い違う人が 2 人いる ◎（記録） | 渡らない |
| 学籍番号を識別キーにする | 重複・出し直しを解決する | 効いた。タイムスタンプと合わせてスクリプトで自動解決できた。**畳んだ量は 11 行**（全 50 行 → 実人数 39 人）◎（記録） | 渡らない |
| 整備スクリプト（Form → スプレッドシート） | 手でエクセルに転記するのをやめる | 効いた。整理はボトルネックでなくなった | 渡らない |
| シフト表を JSON で管理＋リアルタイム表示 | 割り当てを見ながら編集する | 表として見えるところまで。制約チェックと偏り計算は人間に残り、割り当ては依然 3〜6 時間 | 渡らない |
| シフト表確認サイト（Vercel・PC／スマホ対応） | 画像が見づらいのを直す | 作る側の受け取りでは使われなかったが、実際には割れている → 入る側 (1/5) | 渡らない |
| 希望確認画面（提出サイト内のボタン ◎（記録）） | 本人が出した希望を確認できるようにする | 開いた人はいる → 入る側 (1/5)。ただし良し悪しは取れていない △ | 渡らない |

### 確定（◎：インタビューで裏が取れた）

読み手は **HMW**。各項目が答えるのは「解きにいく候補」。

1. 割り当てが全工程で唯一かつ最大のボトルネックになっている ◎
   根拠: 3〜6 時間・3 日がかり・やり直し 20 回規模
   効く先: ACTION 8

2. 調理系の候補が枯れ、公平性を犠牲にしてでも同じ人を入れている ◎
   根拠: 「検便 × 学年（3・4 年）× 時間が合う」の 3 条件で候補が極端に狭まる
   効く先: ACTION 8

3. 準備・片付けの割り当てルールが複雑で、担当者の頭の中にしかない ◎
   根拠: 午前に仕事→準備／午後に仕事→片付け／両方ある人は片方／どちらも無い人は入れない／複数日で準備が偏らないようにする
   効く先: ACTION 8 / 改善機会 15

4. 「公平」の基準が担当者の頭の中にあり、確かめる手段が目視しかない ◎
   根拠: 準備の回数・シフト回数・合計時間のどれを見るかが本人の中でしか決まっていない
   効く先: ACTION 8 / 入る側 改善機会 14
   注意: 量そのものへの不公平感は入る側で否定されている。**シフト時間を均す精度を上げても公平感には届かない**

5. 粗い単位で集めた希望を 30 分枠に割り直す変換が、担当者の頭の中でしか行われていない ◎
   根拠: フォームは粗い単位で聞き、30 分には組むときに割り直している
   効く先: ACTION 4・8

6. 集めたのに使われない希望（「一緒に組めたら嬉しい友達」）がある ◎
   根拠: 余裕がなく考慮していない
   効く先: ACTION 4・8 / 入る側 改善機会 2
   注意: 出す側は捨てられていることを知らず、考慮される前提で書いている

7. 修正のたびに、初回と同じ制約チェック（検便・学年・時間）を手でやり直している ◎
   根拠: 代わりの人を探すのに 3 条件を再チェックしている
   効く先: ACTION 11 / 入る側 改善機会 11・18

8. 割り当ての実体は JSON の手編集であり、支援は「表として見える」ところまでしかない ◎
   根拠: 制約チェックも偏りの計算も人間に残っている
   効く先: ACTION 8

9. 見える化だけでは時間は縮まなかった ◎
   根拠: JSON ＋ リアルタイム表示を作っても 3〜6 時間のまま
   効く先: ACTION 8
   注意: **すでに試して効かなかった手である。** HMW で同じ方向の案を出さない

10. 確認サイトが使われたことが担当者に届いていない ◎
    根拠: 作る側は「サイトは使われなかった」と受け取っているが、実際には割れている → 入る側 (1/5)
    効く先: ACTION 10 / 入る側 改善機会 7・29

11. フォームにログインを付けていないため、提出した本人の手元に希望の控えが残らない ◎
    根拠: ログイン設定を付けると API の制限が厳しくなるため、意図的に外している
    効く先: ACTION 10b / 入る側 改善機会 5
    注意: 「困った」と言った人は入る側に 1 人もいない ◎ ので、控えを目的に何かを作らない

12. 全員分が見えることには反応が出ている ◎
    根拠: 複数人が「全員分見れちゃうんだ」と作る側に直接言っている
    効く先: ACTION 10b / 入る側 改善機会 6
    注意: 言った本人には当たれておらず、特定する道もない △（→ ADR 作る側-0003）。
    反応が拒否感なのか驚きなのかは未検証

13. 生データ（スプレッドシート）をそのまま共有する道が塞がっている ◎
    根拠: 重複行が多く、スマホで見づらい
    効く先: ACTION 10

14. 1 件の変更を反映するのに commit / push / PR / merge が必要で、1 回 10 分かかる ◎
    根拠: Vercel に反映するまでの手順が固定されている
    効く先: ACTION 10・11 / 入る側 改善機会 8・17
    注意: 当日の稼働中にも表を見る人がいるので、差し替えは当日分まで届く必要がある

15. 担当が毎年入れ替わるのに、渡るのは前年のシフト表 1 枚と LINE の一文だけ ◎
    根拠: 引き継ぎは「Google フォームで集めてエクセルで組んだ」という一文と前年のシート
    効く先: ACTION 1

16. 作り込んだものが翌年に一切残らない ◎
    根拠: 「整ったデータの集まるフォームは引き継げない」
    効く先: ACTION 4・7・10 / 改善機会 15

17. 各工程の重さが、その年の担当者の技術力だけで決まってしまう ◎
    根拠: 同じ整備工程が、スクリプトの年とエクセル転記の年で別物になる
    効く先: ACTION 7 / 改善機会 15

18. 必要人数の根拠が「去年と同じ」しかない ◎
    根拠: 妥当性の検証も、翌年への引き渡しもできていない
    効く先: ACTION 3

19. 委員会のルールが文書化されず人伝いに渡っている ◎
    根拠: 検便・学年・クリーンパトロールのどれも口頭か前年度担当者経由
    効く先: ACTION 1・2

20. クリーンパトロールの枠がフォーム作成後に確定するため、枠設計が後から崩れる ◎
    根拠: 名簿はフォーム作成前に来るが、指定枠は後に来る
    効く先: ACTION 2・3

21. 日ごと・年度ごとに営業時刻が変わるため、前年の成果物を再利用できない ◎
    根拠: 準備開始／調理開始／調理終了／片付け開始の 4 つの時刻が毎回変わる
    効く先: ACTION 3

22. 特定も催促もしたうえで、なお締切後の提出が残る ◎
    根拠: 提出記録を見て未提出者を特定し、数人に個別催促している。それでも締切後の提出が 6 人分ある ◎（記録）
    効く先: ACTION 6 / 入る側 ACTION 1
    注意: この機会の中身は「特定していない」ことではない（→ ADR 作る側-0001）。
    催促は締切後に人力で回収しているという意味でもある

23. 担当者が無報酬で、模擬店の他の役割と兼任している ◎
    根拠: 調理・準備・片付けを並行して持っている
    効く先: ACTION 1・9

24. クリーンパトロールをサボる人がいて、その場に居た別の人が肩代わりしている ◎
    根拠: 入る側の目撃証言。作る側は認識のうえで当日吸収していた ○
    効く先: ACTION 12 / 入る側 改善機会 12
    注意: 担当者側の優先度は低い。委員会指定枠に「その枠が実際に実行されるか」という条件を入れる余地はある

25. 30 分ぴったりで刻んだ枠に余裕が無く、遅刻がそのまま次の枠に乗る ◎
    根拠: 入る側の観測。交代・引き継ぎそのものにも時間が要る
    効く先: ACTION 3・12 / 入る側 改善機会 13・15
    注意: これも作る側は認識のうえで当日吸収しているため、担当者側の優先度は低い

26. 事後の申し出が、記録の残らない場所に集まる ◎
    根拠: 申し出は個別 LINE に入るのが既定で、手で処理しない限り何も残らない
    効く先: ACTION 11 / 入る側 改善機会 10・31
    注意: 担当者の記録癖の問題ではなく、経路の置き場所の問題である。
    **HMW で「ちゃんと記録する」を解きにいかない**

27. 未提出者の特定と催促が、作る側の記憶と手作業に乗っている ◎
    根拠: 提出記録は残っているが、照合相手の「誰が学祭に来るはずか」は名簿ではなく頭の中にある
    効く先: ACTION 6 / 入る側 改善機会 20
    注意: 気づかれなければ漏れる △。参加予定者の名簿があれば機械的に出せるが、その名簿が無い

28. 友達欄は、提出の 4 割弱が空欄のまま出されている ◎（記録 15/39）
    根拠: 提出者 39 人のうち記入 24・空欄 15 で、書かれた分は全件が指定どおりの学籍番号 → 入る側 改善機会 3
    効く先: ACTION 4 / 入る側 改善機会 3
    注意: 「指定が守られていない」ではない ◎。落ちているのは書式ではなく入力そのものである。
    弾かれて空にしたのか最初から書かなかったのかは記録では区別できない △（→ ADR 作る側-0006）

29. 一意に辿れる友達欄を要求すると、そのコストは入る側に出る ◎
    根拠: 学籍番号で書いた人が「友達の学籍番号確認が時間かかった」と、そこで止まっている → 入る側 (1/5)
    効く先: ACTION 4 / 入る側 改善機会 25
    注意: バリデーションを厳しくしたこととは別の負荷である。
    記録では学籍番号を書いた人がもう 1 人いる ◎ が、その人が手間を口にしたかは聞いていない △

30. 出した内容を確認しようとする行為は起きている ◎
    根拠: 見返したくなった人が入る側に 2 人いて、片方は希望確認画面で解決している → 入る側 (2/5)
    効く先: ACTION 10b / 入る側 改善機会 27
    注意: 「需要が無い」のか「画面があったので満たされていた」のかが区別できていない（→ ADR 入る側-0002）

31. 友達欄が見えるのは「困らないけど、気まずい」◎ (1/1)
    根拠: 黙って画面を開いた人が「誰と組みたいか番号が見えた」と答えている
    効く先: ACTION 4・10b / 入る側 改善機会 28
    注意: 対処は「自分の分だけ表示」ではなく「友達欄だけ隠す」で足りる。
    ただし実害としては申告されていないので優先度は高くない

32. 申し出が何件あったのかを、記録から復元する道が無い ◎
    根拠: 記録に現れた 1 件は申し出ではなく希望の修正で、LINE 直申告の分は 1 行も現れない ◎（記録）
    効く先: ACTION 11 / 改善機会 26
    注意: 記憶では 1〜2 人だが、記録からは 0 人で確定した（→ ADR 作る側-0005）

33. 作る側を通らない相対交代がある ○（1 件。第三者から聞いた話）
    根拠: 予定が被った人が、サークルの友達と交代してもらって対処したという話がある
    効く先: ACTION 11 / 入る側 改善機会 19
    注意: **この節で唯一の ○ である。** 一次証言ではない。○ 1 件を根拠に打ち手の方向を決めない

34. 出し直しの量は、自動で畳んでいるぶん作る側には見えていない ◎（記録 11/39）
    根拠: 提出記録は全 50 行で実人数は 39 人 → 約 11 人が 2 回出している ◎（記録）。ほぼ締切内 ◎
    効く先: ACTION 7 / 入る側 改善機会 34
    注意: 作る側が締切後の出し直しとして認識しているのは 1 件だけである ◎。残りは工程に乗る前に解決されている

### 否定・縮小された

読み手は **HMW**。各項目が答えるのは「解きにいかないもの」＝ 禁止リストである。
入る側の想定については [入る側.md](入る側.md) の同名の節にある。

- 回答データの整理に人力の変換工程が挟まる → **縮小** ◎（証言者の年はスクリプトで解決済み。例年は未検証 ○）
- 最新版がどれか定まらず、古い表が参照され続ける → **否定** ◎（ノートの画像を差し替えるので古い版は残らない）
- 当日の欠員が担当者の即興対応で吸収され、大きな負担になっている → **否定** ◎（連絡が来る欠席では困っていない）
- 埋まらないコマが出て、その存在に後から気づく → **否定** ◎（代わりに「公平性を欠いてでも埋めた」が起きている）
- 担当者自身の希望が後回しにされ、割り当てで不利になっている → **否定** ◎（入る時間が多いのは幹部だからである）
- 作る側なので自分の希望を後回しにする体験がある → **否定** ◎（負担は割り当ての不利ではなく作業量そのもの）
- 片付けの公平性への配慮を諦めている → **否定** ◎（諦めではなく、必要が薄いという判断）
- 催促が人間関係のコストを伴い、担当者が心理的に負担している → **判定不能** △（催促は実在するが、負担だったかは聞いていない）
- 未提出者の特定に毎回の突き合わせコストがかかる → **成立する** ◎（コストの形が違っただけで、コストはあった）
- 全員分の希望が見えるのは評判が悪かった → **縮小** ○（中身は確定していない）
- 希望確認画面は誰にも使われなかった → **否定** ◎（入る側 1/5 が開いている）
- 希望確認画面は、知られたうえで使われなかった → **判定不能** ◎（「使わなかった」「知らなかった」「使った」が混在）
- 希望確認画面は入る側に届いていない（だから知らせればよい）→ **縮小** ◎（記録。サイトのトップに並んでいた）
- 希望確認画面は好評だった → **取り下げ** ○（「好評」は作る側本人の感覚だった）
- シフトと予定が被った人は、作る側に申し出てくる → **判定不能** ○（迂回されている可能性が 1 件）
- 当日の穴は、連絡が来るものとサボりの 2 種類である → **判定不能** ○（3 種類かもしれない）
- 出し直した人は、出す前に「今から出してもいいか」と聞いてきた → **否定** ◎ (1/1)
- 記録に残っている出し直しは、「希望と違うコマが入った」という申し出である → **否定** ◎ (1/1)
- 当日のサボり・遅刻は担当者に見えていない → **否定** ○（認識のうえで当日吸収していた）

**当初どう書いていたか・何が起きて動いたかは、ここに書かない。**
[`docs/ADR/user-journey-map/`](../ADR/user-journey-map/) にあり、索引は「更新ログ」節にある。

### 未検証（△：まだ誰にも聞けていない）

読み手は **`interview-questions`**。各項目が答えるのは「次にどうすれば埋まるか」。
**この節がそのまま Interview List** として機能するので、専用の置き場所は作らない。
聞きに行く前に `interview-questions` skill（`/interview-questions`）を呼ぶ。
作る側の既存ガイドは [`docs/interviews/02-作る側.md`](../interviews/02-作る側.md)（これから聞く相手も同じファイルを更新して使う）。
**入る側の未検証項目は [入る側.md](入る側.md) の同名の節にある。** こちらには置かない。

- データ整理を手作業でやる場合の所要時間と、フォーム作成のどこで詰まるか △ —
  どうすれば埋まるか: **技術力の低い年の担当者**（前々年度の「手でエクセルに転記」は伝聞どまり ○）
- 他サークル／他年度での進め方 △ — どうすれば埋まるか: **他年度・他サークルの担当者**
  （この学祭で共通の課題なのか、このサークル固有なのかが決まる）
- 催促の心理的コスト △ — どうすれば埋まるか: **この証言者本人**
  （2026-09-13 の時点では「催促していない」と答えていたため、質問が立たなかった）
- 催促した数人が誰で何人か／催促しても出さなかった人がいたか △ — どうすれば埋まるか: **この証言者本人**（記録には残らない）
- 必要人数（調理責任者 1／調理 2／会計 1／呼び込み 2／列整理 2）が妥当だったか △ —
  どうすれば埋まるか: **他年度の担当者**（根拠は「去年と同じ」しかない）
- JSON の変更履歴に何が残っているか △ — どうすれば埋まるか: **この証言者本人**（申し出の件数が復元できるかが決まる）
- 未提出のまま組んだことが、入る側にどう受け取られているか △ — [入る側.md](入る側.md) にも同じ項目がある
