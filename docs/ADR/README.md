# ADR — 判定が動いた記録

**成果物の本文は「今の結論」だけを持つ。** 結論がどう動いたか（それまでどう書いていたか・
何が起きて変わったか）は、**ここに 1 判定 1 ファイルで積む**。

本文に経緯を残すと、既存の全項目に「N 人目まではこうだった → 崩れた」が 1 段ずつ生えて、
**人を 1 人聞くたびに本文が伸びる**。かといって経緯は捨てられない
（「n=4 で確定と書いたものが n=5 で動いた」は、次に読む人が (n/m) をどこまで信用してよいかを決める材料になる）。
git log にはコミットメッセージの粒度しか残らず、**何が何に変わったか・なぜかは追えない**。

## 器の一覧

**この表は ADR だけの表ではない。** **この repo が持つ器の総目録である** — 何をどこに置くかは、ここを見れば分かる。

| 器 | 何を持つ | 規約の原本 |
| --- | --- | --- |
| **成果物の本文**（`docs/journey/<立場>.md` ／ [`docs/hmw.md`](../hmw.md) ／ [`docs/design-doc.md`](../design-doc.md) ／ [`docs/tech-requirements.md`](../tech-requirements.md)） | **今の結論だけ** | 各 skill |
| **`docs/interviews/<連番>-<立場>.md`** | **逐語（一次情報）** — 誰が何と答えたか。**本文には (n/m) のまとめだけが残る** | `interview-questions` skill |
| **記録の隣**（`data/<記録の名前>.md`） | **記録の実体** — 転記した項目の一覧・形式の実体・件数・揃っていないところ。**記録そのものがリポジトリに入っているときだけ置く**（入っていないなら本文が原本） | `tech-requirements` skill の「記録からの転記」 |
| **実機の記録**（[`src/実機で確かめた記録.md`](../../src/実機で確かめた記録.md)） | **本物の環境で走らせた結果** — 実機でしか分からないものの名指しと、手元の検査との対応と、1 回ごとの通った／通らなかった。**手元の検査では分からないものが残るときだけ置く** | [`src/実機で確かめた記録.md`](../../src/実機で確かめた記録.md) の先頭 |
| **`docs/ADR/<対象>/`** | **判定が動いた記録**（それまでの結論 / 何が起きたか / 新しい結論 / 影響） | このファイル |
| **成果物末尾の「更新ログ」節** | **索引** — 1 行（日付・動いたもの・ADR へのリンク）。**成果物が生まれた時点で、空のまま置く**（→「[書くタイミング](#書くタイミング)」） | このファイル |

**どの器も引き受けているのは 1 つである** — **本文に混ぜると、1 回の追加で本文が伸び続けるもの。**
**人を 1 人聞くたびに逐語が、記録を 1 回引き直すたびに実体が、判定が 1 回動くたびに経緯が伸びる。**
**器に出せば、本文に増えるのは在処と結論の行だけになる。**

**器を足したら、この表に 1 行足す。** **skill の中だけに書いて済ませない** — そこにしか無い器は、
**その skill を開いた人にしか見えない。**

### なぜこの一覧がここにあるのか

**置き場の候補は 2 つあり、どちらにも難があった**（issue #123）。

| 候補 | 難 |
| --- | --- |
| **ここ（`docs/ADR/README.md`）** | **この文書は「判定が動いた記録」の規約であって、器の総目録を持つ役ではない** |
| **各 skill に書く** | **5 本に散る。**「規約が局所的で、横に効かない」がそのまま残る（issue #121） |

**ここを採った。** **横断の表がこの repo にはここにしか無く、器の話が 1 か所に集まるからである。**
**役が広がることは受け入れる** — 各 skill に散らしたままにすると、**器が 1 つ増えるたびに 5 本を読み直さないと
全体が分からない状態が続く。**実際、`docs/interviews/` と記録の隣は、**skill が個別に名指ししているだけで、
どこにも一覧が無かった。**

**この表と、以下の ADR の規約は別物である。混ぜない。** 以下は `docs/ADR/<対象>/` 1 行分の規約であって、
**器の総目録ではない。**

## 置き場所

```
docs/ADR/
├── README.md                    ← このファイル
├── _template.md                 ← ADR の雛形
├── user-journey-map/            ← ジャーニーマップの判定が動いた記録
│   ├── 入る側-0001-<slug>.md
│   ├── 入る側-0002-<slug>.md
│   └── 作る側-0001-<slug>.md
├── hmw/                         ← HMW の判定が動いた記録
│   └── 0001-<slug>.md
├── design-doc/                  ← Design Doc の判定が動いた記録
│   └── 0001-<slug>.md
└── tech-requirements/           ← 技術の要件定義の判定が動いた記録
    └── 0001-<slug>.md
```

**第 1 階層は対象**（＝ どの skill / どの成果物の話か）。

| フォルダ | 何を記録する場所か |
| --- | --- |
| `user-journey-map/` | `docs/journey/<立場>.md` の**判定が動いた記録**。記号（◎ / ○ / △）が変わった・(n/m) の読みが変わった・当初の想定が否定された・取り消された |
| `hmw/` | [`docs/hmw.md`](../hmw.md) の**判定が動いた記録**。選んだ改善機会が替わった・採用ソリューションが覆った・却下理由が変わった・候補の束ね方が誤っていた |
| `design-doc/` | [`docs/design-doc.md`](../design-doc.md) の**判定が動いた記録**。7 セクションのどれかの結論が変わった・スコープの内外が入れ替わった・要件の前提が崩れた・△ が増減した |
| `tech-requirements/` | [`docs/tech-requirements.md`](../tech-requirements.md) の**判定が動いた記録**。技術選定が覆った・仕様が変わった・**完了の測り方が変わった**・△ が増減した |

今後 `interview-questions/` が増えても、**同じ形で第 1 階層に足す**。
**フォルダを足したら、この表にも 1 行足す。** ここが薄いと「なんの ADR か分からない」に戻る。
**いつ足すのかは「[書くタイミング](#書くタイミング)」**。

## ファイル名

`<立場>-<連番>-<slug>.md`

- **連番は立場ごとに 0001 から**振る。**欠番を詰めない・振り直さない**
- **立場をフォルダにせず、ファイル名の先頭に置く。** 立場は少数なので階層を 1 段増やすほどの量にならない。
  先頭に置けば `ls` で立場ごとに固まる
- `<立場>` 部分は対象によって変わる（`user-journey-map/` では `docs/journey/<立場>.md` の立場名）
- **成果物が 1 本しか無い対象では、`<立場>` を省いて `<連番>-<slug>.md` にする**（`hmw/` は [`docs/hmw.md`](../hmw.md) 1 本なので `0001-<slug>.md`）。**分ける先が無いのに固定の接頭辞を全ファイルに付けても、`ls` が固まらない**

## 本文からの参照の書き方

**`ADR 入る側-0001` と書く。** 番号だけでは対象が分からない。
**`<立場>` を省いた対象では、代わりに対象名を置く**（`ADR hmw-0001`）。

## Status

| Status | 意味 |
| --- | --- |
| 有効 | この ADR の「新しい結論」が現在の結論である |
| 取り消し（`ADR <立場>-NNNN` が上書き） | 後続の ADR に上書きされた |

**判定は一度戻ることがある。** 上書きした ADR と上書きされた ADR は**相互にリンクする**
（上書きした側の「それまでの結論」に元の ADR を、上書きされた側の Status に新しい ADR を書く）。

## 書くタイミング

**本文を削る前に ADR を書く。** 先に本文から抜くと、抜いた瞬間に情報が消える。

### フォルダは、最初の 1 本と同じ変更で作る

**`docs/ADR/<対象>/` は、その対象の最初の 1 判定が出たときに作る。空のフォルダを先に置かない。**
空ディレクトリは git に乗らないので、先に作っても commit に含まれず、手元にしか存在しない状態になる。

**フォルダ・最初の 1 本・「第 1 階層は対象」の表の 1 行は、3 つセットで同じ変更に入れる。**

- フォルダが無いのに表だけ増やすと、README が**実体の無い行**を持つ
- フォルダだけ作って表に足さないと、「なんの ADR か分からない」に戻る

**まだ 1 本も無い対象は、README に行を作らなくてよい。** 置き場所が `docs/ADR/<対象>/` になることは
この README が決めているので、行が無いこと自体は欠落ではない。

### 更新ログ節は、成果物が生まれた時点で置く

**フォルダとは逆に、成果物末尾の「更新ログ」節は ADR が 0 本でも置く。**
節ごと無いと、最初の 1 本が出たときに「索引をどこに足すのか」から始まることになる。
中身は空のまま（見出し ＋ 空の表）でよい。
