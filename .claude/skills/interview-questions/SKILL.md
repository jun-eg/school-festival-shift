# インタビュー質問リストを作る

> 「**この相手に、今回、何を何問聞くか**」を決めて、相手 1 人分のインタビューガイドを出す。

```
【何を聞くか（この skill）】  →  どう聞くか（references/interview.md）  →  聞いた結果をマップに戻す（user-journey-map 手順 6）
```

これは一直線の工程ではなく、**ワーク → インタビュー → ワーク**のサイクルの中に入る。
質問の発生源はジャーニーマップだけではなく、**Design Doc を書く過程も含む**。

- **入力**: `docs/user-journey-map.md` の **△（未検証）** と **○（伝聞・本人の推測）**、および「解像度が荒い部分」節。Design Doc を書いていて分からなかった点も同じ扱い
- **出力**: `docs/interviews/<連番>-<相手の立場>.md` — 相手 1 人分のインタビューガイド（見出し + 質問 + 順序 + 送る文 + 質問↔仮説の対応表）

## 守備範囲

**質問リスト（ガイド初版）を作るところまで。**
実施後の集計・マップへの反映はこの skill の仕事ではなく、`user-journey-map` の手順 6 で行う。

## Interview List を別に持たない

資料上は、質問を溜める専用のシートを別に持つ前提になっている。**このリポジトリでは作らない。**

`docs/user-journey-map.md` の以下 2 つが、すでに Interview List として機能しているため。

- **「解像度が荒い部分（インタビューで聞く）」節** — 書いていて想像で埋めた部分がそのまま溜まっている
- **「未検証（△）」節**、および本文中の **○（伝聞・本人の推測）** の記号

この skill は**そこを入力として読む**。Design Doc 側に同じ受け皿を置くかは別途判断する。

## 手順

### 0. 相手と経路を確定する

**ここが「この相手に、今回、何を何問聞くか」の本体。** 未確定のまま質問を書き始めない。

決めること:

- **相手の立場**（作る側／入る側）と属性。属性を散らす軸を表にする（例: 調理か否か / 学年 / 提出タイミング / 事後申告）
- **何人目か。1 人目はパイロット扱いにする**（手順 6）
- **経路と往復数**

#### 人数の基準

- **5〜6 人**で新しい発見が出にくくなる。そこが目安
- **5 人未満は「対象者が少なすぎる」失敗**に当たる
- **現状は 3 人（作る側 1・入る側 2）で未達。** 当面は残り 2〜3 人を埋める前提で組む

#### 経路によって質問の作りが変わる

| 経路 | 往復 | 1 問の作り | 問数の目安 |
| --- | --- | --- | --- |
| **対面・通話**（半構造化 × デプス） | 追い質問あり | **1 質問 1 回。** 深掘りは現場でやる | **持ち時間 30 分**が目安。見出し 4〜6 × 本命 1 問 |
| **LINE 等の一発送信** | 1 往復・追い質問なし | **1 問に「何をしたか」と「なぜそうしたか」を両方入れる**（1 質問 1 回の唯一の例外） | 10 問前後 |

> LINE 経路では深掘りができない分、**人を散らすことで精度を出す。** 属性が重なった相手ばかりだと同じ答えしか出ない。

### 1. 目的を 3 要素で文章化する

曖昧なまま始めると質問が発散する。以下 3 つを文章にしてから先へ進む。

1. **ターゲット** — 誰に聞くか（ペルソナ、または今回の相手の立場）
2. **課題・悩み** — 検証したい改善機会
3. **解決アイデア** — HMW の前なら**空欄でよい**。空欄なら目的は自動的に「ニーズの把握」側になる

あわせて、`references/interview.md` の**目的 2 つ（ニーズの把握 / ソリューションの改善）のどちらかに決める。**
**両方を 1 回に混ぜない。**

### 2. 検証したい仮説を洗い出す

**粗くていい。精度より多角性。** この時点では質問の形にしない。1 行 1 仮説で並べる。

- 入力は `docs/user-journey-map.md` の **△（未検証）** と **○（伝聞・本人の推測）**
- **○ は「1 人の証言を全員の話にしていないか」を疑う仮説として立てる。**
  「希望確認画面は好評だった」がこの型で崩れた（出所が本人の感覚だった）
- 仮説の精度にこだわって準備が止まるのが、この手順の失敗

### 3. 仮説ごとに質問を割り当てる

- **まずクローズドエンド質問を 1 質問 1 枚で書き出す。** 事実から入る（事実 → 判断 → 感情 → 背景）
- **各仮説に最低 1 問。** 対応が取れない仮説は、検証できないまま終わる
- **広く浅く聞く。** 狭く深く聞くと、想定外のセグメント・課題を取りこぼす

### 4. グループ化して、見出しと順序を決める

1. 似た質問をまとめ、**見出しを付ける**。**仮説 = 見出し**に対応させる
2. 見出しごとに**オープンエンドの本命質問を 1 問**設計する
3. **左から右へ並べて流れが自然か確認する。** 並びは 導入 → 事実（クローズド）→ 行動 → 判断・感情 → 背景 → まとめ
4. **クローズドエンド → オープンエンド**の順に配置してガイド初版にする

#### ① 導入ブロック

ベーシックな質問リストは ② 背景・状況 から始まっており **① が欠番**。ここで埋める。

- **何のために聞くか**を一言。所要時間か問数を添える
- **「分かるやつだけでいい」「正直に面倒だったでいい」と明記する。**
  全部答えさせようとすると既読スルーされる
- **自分の苦労は言わない。** 言うと相手から不満が出てこなくなる
- **自作したものを擁護しない。** 使われなかった理由が聞きたい

### 5. 危ない聞き方を潰す

出したガイドを、1 問ずつ以下で点検する。

| 見るところ | 落ちていたら |
| --- | --- |
| **Yes/No で終わる質問**になっていないか | **誘導質問に当たる。** 開いた形に直す（※ 手順 4 の助走として意図的に置くクローズドは可） |
| **仮説をそのまま聞いて**いないか | 「〇〇が不便ですよね？」→ 事実を聞く形に直す |
| **否定的な聞き方**になっていないか | ×「なぜ使わないんですか」→ ○「どんなときに使わないと思いますか」 |
| **1 問に質問が 2 つ以上**入っていないか | 分ける（※ LINE 一発送信は手順 0 の例外） |
| **ソリューション案の評価**を聞いていないか | ニーズ把握の回では聞かない（「自動で組めたら嬉しい？」の類） |
| **意見を聞いて**いないか | 「どう思う？」→「前回どうした？」。過去の実際の行動に直す |
| **重要な質問が抜けて**いないか | 手順 2 に戻り、質問が 1 問も紐づいていない仮説が無いか確認する |
| **流れが不自然**でないか | 見出しの並びを頭から読み、話題が飛んでいないか確認する |
| **1 問あたりの所要時間**を見積もったか | 対面 30 分に収まるか。収まらなければ仮説の数を削る |

### 6. 1 人目が終わったらガイドを直してから 2 人目に行く

パイロット調査を、この規模に合わせて読み替える（専用の 1 人を使うのは重いので、**1 人目を実質パイロット扱いにする**）。

- **事前に決めておく**: 追加質問をどこまで足してよいかのルール、記録の取り方（誰が書くか）。
  決めずに始めると、人によって聞いた内容がばらつく
- **1 人目で測る**: 取れなかった質問 / 答えが割れた質問 / 誤解された質問 / **各質問に何分かかったか**
- **同じファイルを更新して commit する。** どこをどう直したかが履歴に残る
- ただし**質問を変えると人ごとの比較ができなくなる。** 変えたなら「2 人目から変えた」と本文に残す

## 失敗の扱い

| 起きること | どうするか |
| --- | --- |
| **聞いた結果、前提が崩れた** | 質問リストを直すのではなく、**手順 1（目的 3 要素）まで戻る。**「なぜ好評だったのか」→「そもそも需要があるのか」のように、問い自体を組み替える |
| **○（伝聞・本人の感覚）を ◎ の代わりに使っていた** | **出所を聞く質問を立てる**（「誰に言われたか」「直接聞いたのか」） |
| **1 人の証言を全員の話にしている** | マップ側の **(n/m) 表記**に合わせ、対応表にも何人に聞いた仮説かを書く |
| **追い質問ができない経路** | 深掘りの代わりに**人を散らす**（手順 0）。1 問に「何を / なぜ」を両方入れる |
| **聞けなかった項目がある** | **△ のまま残す。** 埋まったことにしない |
| **仮説が割れた（該当が半々）** | 集計はこの skill のスコープ外。戻り先だけ示す = **手順 1 の 3 要素まで戻る** |

## 出力フォーマット

`docs/interviews/<連番>-<相手の立場>.md` に書き、**issue コメントにも貼る。** 質問の変遷が git 履歴に残る。

**「各質問が埋めるもの」の表には、該当／非該当の列を空で用意しておく。**
数えるのはこの skill の仕事ではないが、**器をここで作っておかないと後から数えられない。**

````markdown
# インタビュー質問リスト — <相手>（<経路>）

| 項目 | 内容 |
| --- | --- |
| 目的 | ニーズの把握 / ソリューションの改善 |
| 3 要素 | ターゲット / 課題 / 解決アイデア |
| 経路・往復 | LINE 一発送信・1 往復（追い質問なし） |
| 人数 | n 人目 |

## 誰に聞くか（散らし方）
| 軸 | 散らしたい内容 |

## 送る文（コピペ用）
```（導入ブロック + 番号付きの質問）```

## 各質問が埋めるもの（自分用。送らない）
| # | 検証する仮説 | マップの該当箇所 | 該当 | 非該当 |

## 避ける聞き方
| ✗ 聞かない | ○ 代わりに |
````
