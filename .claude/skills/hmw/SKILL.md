# HMW（How Might We...?）

> 課題を『私たちはどうすれば〜できるだろうか？』という問いに変換し、そこから解決策を決める。

アイデア出しフレームワーク 3 ステップの **2 つ目**。

```
ユーザージャーニーマップ  →  【HMW】  →  Design Doc
```

- **入力**: `docs/user-journey-map.md` の改善機会リスト
- **出力**: `docs/hmw.md` — 採用するソリューション 1 つ ＋ **採らなかった候補とその却下理由**（Design Doc の Alternatives Considered になる）

入力の `docs/user-journey-map.md` が無い、または改善機会リストが空なら、**ここから始めない**。先に `user-journey-map` skill を回す。

## How / Might / We の意味

3 つの語にそれぞれ役割がある。問いを書くときに毎回確認する。

- **How** — 解決策を 1 つに決め打ちしない。「どうすれば」であって「〇〇を作れば」ではない
- **Might** — 唯一解ではなく**あり得る解**を探す。外れてよい前提で数を出す
- **We** — 共同作業。誰か 1 人が正解を出す場ではない

## 手順

### 1. 改善機会を 1 つ選ぶ

`docs/user-journey-map.md` の改善機会リストから、ソリューションに繋がりそうなものを **1 つ**ピックアップする。

- **正解はない。決めでよい。** 選べずに止まるのが一番よくない
- 複数を同時に扱わない。混ぜると問いも解決策もぼやける
- 迷ったら、FEELING ADJECTIVE のネガティブが集中していた箇所に紐づくものを選ぶ

選んだ理由を 1 行書き残す（後で問いを選び直すときの手がかりになる）。

### 2. 問いを量産する

下の 9 つの型を使って「私たちはどうすれば〜できるだろうか？」を**書き殴る**。

- **全部の型を埋める必要はない。** 出ない型は飛ばしてよい
- **Write as many HMWs as you can** — 質より数。1 つの型から複数出してよい
- **Make multiple drafts** — 後から問いを書き換えてよい。最初の 1 本に固執しない

#### Be broad, but don't be too broad

問いの幅は、**複数の解決策を許容する程度に広く、指針になる程度に狭く**する。

- 広すぎる例: 「どうすればシフト作成をよくできるだろうか？」→ 何も指していないので解決策が出ない
- 狭すぎる例: 「どうすれば希望入力フォームに締切リマインダーを付けられるだろうか？」→ 解決策が問いに埋まっている（How の役割を潰している）
- ちょうどよい例: 「どうすれば催促しなくても希望が集まるようにできるだろうか？」

#### HMW の 9 つの型

| 型 | 考え方 | 問いの作り方の例 |
| --- | --- | --- |
| Amp up the good | 問題の中のポジティブな要素を解決策に使う | うまくいっている部分を見つけ、それを増幅できないか問う |
| Explore the opposite | 問題の逆を解決する方法を考える | 「困らせる」側に振り切ったらどうなるかを問い、裏返す |
| Remove the bad | ネガティブな部分を完全に取り除く | その作業自体を無くせないかを問う |
| Go after the adjective | ネガティブな形容詞をポジティブな言葉に変える | FEELING ADJECTIVE の「面倒」を「あっという間」に置き換えて問う |
| Create an analogy | この体験を他の体験に例える | 「〇〇のような体験にできないか」と別ドメインに例えて問う |
| Identify unexpected resources | 問題文に書かれていないリソースで解けないか | 人・時間・既存の仕組みなど、使っていない資源を持ち出して問う |
| Break the point-of-view into pieces | 視点をバラバラに分解する | ペルソナ・タスク・場面を分解し、部分ごとに問う |
| Change a status quo | プロセスを完全に変える | 今のやり方をやめて別のやり方にしたらどうかを問う |
| Question an assumption | 必要だと思われているプロセスを削除・変更する | 「そもそもこれは要るのか」を問う |

### 3. 各問いに対してソリューション候補を出す

量産した問いのうち、筋がよさそうなものを選んで解決策を書く。

- **HMW → ソリューションの間にはジャンプが必要。** 論理的に導出されるものではない
- ここは**決めに行く工程**。きれいに繋がらなくても、候補を書いて先に進む
- **埋まらないまま止めない。** 出なければ手順 2 に戻って問いを変える／増やす
- 1 つの問いから複数の候補を出してよい。候補は最低 3 つは並べる

### 4. 1 つに決める

候補の中から採用するソリューションを **1 つ**選ぶ。

書き残すのは 2 つ。

1. **採用理由** — なぜこれを選んだのか
2. **採らなかった候補それぞれの却下理由** — 候補ごとに 1 行以上

#### 却下した候補を消さない

**却下候補と理由は、Design Doc の Alternatives Considered の入力になる。** ここで捨てると後工程が埋まらなくなり、Design Doc が「なぜ他の案ではないのか」に答えられなくなる。

- 「なんとなく違う」で済ませない。何が足りなかったのかを書く
- 採用案が後で覆ったときに戻る先にもなる
