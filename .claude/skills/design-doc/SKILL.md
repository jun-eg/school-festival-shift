# Design Doc

> これから行う取り組みの Why / What / How を 1 本にまとめ、作るものを確定させる。

アイデア出しフレームワーク 3 ステップの **3 つ目（最終成果物）**。

```
ユーザージャーニーマップ  →  HMW  →  【Design Doc】
```

- **入力**: `docs/journey/<立場>.md` **全本**（ジャーニーマップ・ペルソナ・改善機会。立場ごとに 1 本ある）、`docs/hmw.md`（採用ソリューション・却下候補）
- **出力**: `docs/design-doc.md` — 作るものが確定した Design Doc
- **雛形**: `docs/design-doc-template.md` をコピーして書き始める

入力の `docs/hmw.md` が無い、または採用ソリューションが決まっていないなら、**ここから始めない**。先に `hmw` skill を回す。

## Design Doc とは

これから行う取り組み（実験・実装・プロジェクト・プロセス改善）の基本的な要点をまとめたドキュメント。**ソフトウェアの仕様書・設計書とは別物**。Why / What / How と、実装戦略・主要な設計上の決定・その際のトレードオフに重点を置く。これを元にエンジニアが Tech Doc を書き、デザイナーがデザインを始める。

存在意義は 3 つ。

1. **Define** — 他メンバーが実装・サポートできるよう詳細を明確化する
2. **Align** — ステークホルダー間の合意を形成する
3. **リファレンス** — いつ何をどう決めたかを後から思い返せるようにする

## 7 セクションと入力元

| # | セクション | 書く内容 | 入力元 |
| --- | --- | --- | --- |
| 1 | Overview（概要） | 取り組みを一言で | — |
| 2 | What we provide（何をつくるのか） | 何を作り、どう機能し、どんな価値を届けるか。最もシンプルな言葉で | HMW で決めたソリューション |
| 3 | BackGround（バックグラウンド） | なぜやると決めたのか、どんな考察が意思決定を促したのか | **ジャーニーマップ ＋ HMW** |
| 4 | User Story（ユーザーストーリー） | 届ける相手の心境・動機。その動機がどう満たされ、どんな状態になるか | ペルソナ ＋ ユーザーインタビュー結果 |
| 5 | Alternatives Considered（検討した代替案） | 他に取り得た How と、選ばなかった理由 | **HMW で出して採らなかった候補** |
| 6 | Functional Requirements（機能要件：MVP） | **ここで初めて**「何を」構築するかを詳細に要件定義する。実装者向けの設計図 | — |
| 7 | Mile Stone（マイルストーン） | MVP をどう実現するかの時間軸プラン | — |

## 手順

### 1. 入力を揃える

書き始める前に手元に置く。無いまま埋めにいかない。

- `docs/journey/<立場>.md` — ペルソナ、ジャーニーマップ、改善機会リスト。**立場ごとに 1 本あるので全部揃える**
- `docs/hmw.md` — 採用したソリューション、**採らなかった候補と却下理由**（どの立場のマップの改善機会から選んだかが書いてある）

### 2. テンプレートをコピーする

`docs/design-doc-template.md` を `docs/design-doc.md` にコピーし、ガイドの引用ブロック（`>` で始まる部分）を読みながら埋めていく。埋めたセクションのガイドは消してよい。

### 3. 2 → 3 → 4 → 5 の順で埋める

**1. Overview は最後に書く。** 全体が固まらないと一言にまとまらない。

- **2. What we provide** — HMW の採用ソリューションを、価値の言葉に言い換える
- **3. BackGround** — どの改善機会を拾い、どの HMW の問いに変換したのかを辿れるように書く
- **4. User Story** — ジャーニーマップのペルソナをそのまま使う。Before → After の状態変化を書く。
  **主役は、HMW で選んだ改善機会の立場のペルソナ。** 採用ソリューションが他の立場の体験も変えるなら、
  **その立場のペルソナでも User Story を書く**（新しいペルソナを Design Doc 側で発明しない。
  `docs/journey/<立場>.md` にあるものを使う）。体験が変わらない立場を書くかは下の判定に従う。
  書いていて「ここは想像で埋めた」と気づいたら、**その場で `interview-questions` skill を呼んで質問を起こす**。
  質問の発生源はジャーニーマップだけではなく、**Design Doc を書く過程も含む**
- **5. Alternatives Considered** — HMW の却下候補を表に移す。**却下理由を落とさない**

#### 体験が変わらない立場を User Story に書くか

「他の立場の**体験も変えるなら**書く」だけでは、**体験が変わらない立場**の扱いが決まらない。
「変わらないから当てはまらない」とも「変えないこと自体が要件だから書く」とも読めるので、次で判定する。

- **その立場のコストを上げないことが採用理由に入っているなら、体験が変わらなくても書く。**
  `docs/hmw.md` の採用理由に「◯◯側の出入口を動かさない」のような項目が立っているなら、
  変わらないことは副作用ではなく**要件**である。doc に載っていなければ、
  実装が進んだあとに手数が増えても誰も気づけない
- **却下候補の判断基準に使った立場は書く。** 「◯◯側のコストを上げるから却下した」と
  5. Alternatives Considered に書くなら、**その立場が 4 に居ないと辻褄が合わない**
- **書かないと決めたなら、書かない理由を 1 行残す。**
  「検討し忘れた」のか「検討して外した」のかが、読み手に区別できるようにする

書くと決めたら、「**何が変わらないか**」の短い節にする。長く書かない。

- **冒頭で「この立場は Before = After である」と断る。** 変化を探して読ませない。
  状態変化の無い Story で粒度が揃わないのではなく、**揃わないことをこの節が主張する**
- 変わらないもの（集める口・配る口・手数）を名指しし、その立場に
  **新しい入力・判断・操作を足さない**ことを、却下候補の理由と対応させて書く
- 壊れていない状態（例: 「5 人とも希望どおりに入れている ◎ (5/5)」）を挙げ、
  **それを壊さないことが要件である**と書く
- **「変わらない」を「その立場の改善機会が解決した」と書かない。**
  解いていない改善機会は `docs/hmw.md` の「この案が解かないもの」のまま、
  6. Functional Requirements の**スコープ外**に残す

### 4. 6. Functional Requirements を書く

**ここで初めて**「何を作るか」を詳細化する。1〜5 で合意した価値を MVP の機能に落とす。

- スコープ外（今回やらないこと）も書く。境界が曖昧だと Align が効かない
- 小さくまとまらない。ギリギリ届くくらいの射程にする（ただし動くこと）

### 5. 7. Mile Stone を書く

MVP をどう実現するかの時間軸プラン。動くものが出てくる順に並べる。

### 6. 1. Overview を書いて、レビュー観点で読み返す

下の 5 点で自分の Design Doc をレビューする。引っかかったら該当セクションに戻る。

## レビュー観点

### 1. Functional Requirements より前のセクションで「何を作るか」を書かない

BackGround / User Story で機能の話が始まっていたら**差し戻す**。1〜5 は「なぜ」と「どんな価値か」の話で、機能の詳細は 6 の仕事。

### 2. 「モノ」ではなく「価値」に向き合う

- ✕「シフト登録機能をつくろう」
- ◎「◯◯がラクになる」

機能の列挙になっていたら、価値の言葉に引き上げる。

### 3. 妄想の課題を作らない

実在しない困りごとを前提にしていないか。ジャーニーマップ／ユーザーインタビューで裏が取れているか。取れていない箇所は、そう明記するか、聞きに行く。

**聞きに行くと決めたら `interview-questions` skill を呼ぶ**（`/interview-questions`）。
「何を何問聞くか」は目的 3 要素 → 仮説 → 質問の順で降ろす。裏付けが足りない箇所がそのまま仮説の入力になる。

### 4. 1 回で完璧にしない

サイクルを回す前提。**1 周目は粗くてよい。** 完成度を上げようとして止まるのが一番よくない。

### 5. 小さくまとまらない

**ギリギリ届くくらいの射程にする（ただし動くこと）。** 安全側に倒して縮めた MVP は、価値が検証できない。

## 成果物のフォーマット

`docs/design-doc-template.md` の見出し構成をそのまま使う。

```markdown
# Design Doc: <取り組みの名前>

## 1. Overview（概要）
## 2. What we provide（何をつくるのか）
## 3. BackGround（バックグラウンド）
## 4. User Story（ユーザーストーリー）
## 5. Alternatives Considered（検討した代替案）
## 6. Functional Requirements（機能要件：MVP）
## 7. Mile Stone（マイルストーン）

## 更新ログ
```

**Design Doc は 1 本にする。** 機能ごとに分けない。分けると BackGround と User Story が重複し、「なぜこれをやるのか」の合意が取れる単位がドキュメントの外に出てしまう。

機能の粒度の話は 6. Functional Requirements の中で扱う。1 本に収まらないほど大きいと感じたら、それは MVP のスコープが広すぎるサインなので、ドキュメントを割るのではなく 6 のスコープを絞る。

### 更新ログ節

**末尾の `## 更新ログ` は、7 セクションのどれかの判定が動いたときの索引**
（スコープが変わった・採用した How が覆った・User Story の前提が崩れた、など）。
`docs/design-doc.md` を起こした時点では ADR が 0 本なので、**見出しと空の表だけ置く**。
判定が動いたら ADR を 1 本起こし、ここに **1 行（日付・動いたもの・ADR へのリンク）**足す。
**ここに理由・経緯を書き始めたら、それは ADR に書くもの。**

置き場所（`docs/ADR/design-doc/`）・フォルダを作るタイミング・ファイル名・連番・Status・参照の書き方は
[`docs/ADR/README.md`](../../../docs/ADR/README.md)、雛形は [`docs/ADR/_template.md`](../../../docs/ADR/_template.md)。
**規約をここに書き写さない。**

- [ ] 2. What we provide が HMW の採用ソリューションと対応している
- [ ] 3. BackGround がジャーニーマップの改善機会と HMW の問いから書かれている
- [ ] 4. User Story のペルソナが `docs/journey/<立場>.md` のペルソナと一致している（Design Doc 側で新しく作っていない）
- [ ] ソリューションが影響する立場が複数あるなら、**各立場の User Story が書かれている**

- [ ] 体験が変わらない立場の節は、**冒頭で Before = After と断って**いて、「その立場の改善機会が解決した」と書いていない

- [ ] 2 が「モノ」ではなく「価値」の言葉で書かれている
- [ ] 前提にしている課題の裏付け（ジャーニーマップ／インタビュー）がある
- [ ] 6 にスコープ外が書かれていて、MVP が小さくまとまりすぎていない
