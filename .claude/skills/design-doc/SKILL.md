# Design Doc

> これから行う取り組みの Why / What / How を 1 本にまとめ、作るものを確定させる。

アイデア出しフレームワーク 3 ステップの **3 つ目（最終成果物）**。

```
ユーザージャーニーマップ  →  HMW  →  【Design Doc】
```

- **入力**: `docs/user-journey-map.md`（ジャーニーマップ・ペルソナ・改善機会）、`docs/hmw.md`（採用ソリューション・却下候補）
- **出力**: `docs/design-doc.md` — 作るものが確定した Design Doc
- **雛形**: `docs/design-doc-template.md` をコピーして書き始める

入力の `docs/hmw.md` が無い、または採用ソリューションが決まっていないなら、**ここから始めない**。先に `hmw` skill を回す。

## Design Doc とは

これから行う取り組み（実験・実装・プロジェクト・プロセス改善）の基本的な要点をまとめたドキュメント。**ソフトウェアの仕様書・設計書とは別物**。Why / What / How と、実装戦略・主要な設計上の決定・その際のトレードオフに重点を置く。これを元にエンジニアが Tech Doc を書き、デザイナーがデザインを始める。

存在意義は 3 つ。

1. **Define** — 他メンバーが実装・サポートできるよう詳細を明確化する
2. **Align** — ステークホルダー間の合意を形成する
3. **リファレンス** — いつ何をどう決めたかを後から思い返せるようにする

## 7 セクションと入力元

| # | セクション | 書く内容 | 入力元 |
| --- | --- | --- | --- |
| 1 | Overview（概要） | 取り組みを一言で | — |
| 2 | What we provide（何をつくるのか） | 何を作り、どう機能し、どんな価値を届けるか。最もシンプルな言葉で | HMW で決めたソリューション |
| 3 | BackGround（バックグラウンド） | なぜやると決めたのか、どんな考察が意思決定を促したのか | **ジャーニーマップ ＋ HMW** |
| 4 | User Story（ユーザーストーリー） | 届ける相手の心境・動機。その動機がどう満たされ、どんな状態になるか | ペルソナ ＋ ユーザーインタビュー結果 |
| 5 | Alternatives Considered（検討した代替案） | 他に取り得た How と、選ばなかった理由 | **HMW で出して採らなかった候補** |
| 6 | Functional Requirements（機能要件：MVP） | **ここで初めて**「何を」構築するかを詳細に要件定義する。実装者向けの設計図 | — |
| 7 | Mile Stone（マイルストーン） | MVP をどう実現するかの時間軸プラン | — |

## 手順

### 1. 入力を揃える

書き始める前に手元に置く。無いまま埋めにいかない。

- `docs/user-journey-map.md` — ペルソナ、ジャーニーマップ、改善機会リスト
- `docs/hmw.md` — 採用したソリューション、**採らなかった候補と却下理由**

### 2. テンプレートをコピーする

`docs/design-doc-template.md` を `docs/design-doc.md` にコピーし、ガイドの引用ブロック（`>` で始まる部分）を読みながら埋めていく。埋めたセクションのガイドは消してよい。

### 3. 2 → 3 → 4 → 5 の順で埋める

**1. Overview は最後に書く。** 全体が固まらないと一言にまとまらない。

- **2. What we provide** — HMW の採用ソリューションを、価値の言葉に言い換える
- **3. BackGround** — どの改善機会を拾い、どの HMW の問いに変換したのかを辿れるように書く
- **4. User Story** — ジャーニーマップのペルソナをそのまま使う。Before → After の状態変化を書く
- **5. Alternatives Considered** — HMW の却下候補を表に移す。**却下理由を落とさない**

### 4. 6. Functional Requirements を書く

**ここで初めて**「何を作るか」を詳細化する。1〜5 で合意した価値を MVP の機能に落とす。

- スコープ外（今回やらないこと）も書く。境界が曖昧だと Align が効かない
- 小さくまとまらない。ギリギリ届くくらいの射程にする（ただし動くこと）

### 5. 7. Mile Stone を書く

MVP をどう実現するかの時間軸プラン。動くものが出てくる順に並べる。

### 6. 1. Overview を書いて、レビュー観点で読み返す

下の 5 点で自分の Design Doc をレビューする。引っかかったら該当セクションに戻る。

## レビュー観点

### 1. Functional Requirements より前のセクションで「何を作るか」を書かない

BackGround / User Story で機能の話が始まっていたら**差し戻す**。1〜5 は「なぜ」と「どんな価値か」の話で、機能の詳細は 6 の仕事。

### 2. 「モノ」ではなく「価値」に向き合う

- ✕「シフト登録機能をつくろう」
- ◎「◯◯がラクになる」

機能の列挙になっていたら、価値の言葉に引き上げる。

### 3. 妄想の課題を作らない

実在しない困りごとを前提にしていないか。ジャーニーマップ／ユーザーインタビューで裏が取れているか。取れていない箇所は、そう明記するか、聞きに行く。

### 4. 1 回で完璧にしない

サイクルを回す前提。**1 周目は粗くてよい。** 完成度を上げようとして止まるのが一番よくない。

### 5. 小さくまとまらない

**ギリギリ届くくらいの射程にする（ただし動くこと）。** 安全側に倒して縮めた MVP は、価値が検証できない。

## 成果物のフォーマット

`docs/design-doc-template.md` の見出し構成をそのまま使う。

```markdown
# Design Doc: <取り組みの名前>

## 1. Overview（概要）
## 2. What we provide（何をつくるのか）
## 3. BackGround（バックグラウンド）
## 4. User Story（ユーザーストーリー）
## 5. Alternatives Considered（検討した代替案）
## 6. Functional Requirements（機能要件：MVP）
## 7. Mile Stone（マイルストーン）
```

対象が大きく 1 本に収まらない場合は、Design Doc を機能ごとに分割してよい。その場合も 7 セクションの構成は各ドキュメントで維持する。

## 完了チェック

- [ ] 7 セクションがすべて埋まっている（空のセクションを残さない）
- [ ] 2. What we provide が HMW の採用ソリューションと対応している
- [ ] 3. BackGround がジャーニーマップの改善機会と HMW の問いから書かれている
- [ ] 4. User Story のペルソナがジャーニーマップのペルソナと一致している
- [ ] 5. Alternatives Considered に HMW の却下候補と**却下理由**が入っている

- [ ] 2 が「モノ」ではなく「価値」の言葉で書かれている
- [ ] 前提にしている課題の裏付け（ジャーニーマップ／インタビュー）がある
- [ ] 6 にスコープ外が書かれていて、MVP が小さくまとまりすぎていない
