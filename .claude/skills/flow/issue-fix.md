# issue-fix

> issue の目的と解決策の食い違いを、直して再判定する周回に乗せる。

手を 2 本に分ける。判定するのは `issue-reviewer`、直すのは `issue-fixer`（[`.claude/agents/`](../../agents/)）。
**判定する手と直す手を分ける。** 回している側は本文を直さない。直す手は issue-fixer だけで、issue-reviewer は何も書き換えない。

- **入力**: issue 番号か URL が 1 つ。`/flow issue-fix 312`。続けて所見（implementer・pr-reviewer の返答か、人の指示）があれば、それも渡される
- **出力**: 直した issue と周回ごとの判定を載せた人への報告

## 手順

### 1. 引数をほどき、入口を選ぶ

```
bash .claude/skills/flow/fetch.sh <番号か URL>
```

番号・タイトル・state・親・sub-issue が JSON で出る。URL なら owner/repo も URL から取る。

役割は JSON から決める。`subIssues` があれば `親`、`parent` があれば `sub-issue`（所見なし入口の最初の判定では親まで遡らない）、どちらも無ければ `単独`。

| 入口 | 条件 | 始める手 |
| --- | --- | --- |
| 所見あり | 所見が渡されている | issue-fixer から（手順 2）。渡された issue が CLOSED なら fixer を回さず、手順 3 の判定だけ |
| 所見なし | 番号だけ。起票直後の点検 | issue-reviewer から（手順 3）。判定が妥当なら何も書き換えない |

**state が CLOSED の issue は、役割が何でも（入口が何でも）判定だけして直さない。** 終わった物を書き換えない。判定は報告に残す。

### 2. issue-fixer を回す

Agent tool で `subagent_type: issue-fixer`。prompt には次を入れる。

- issue 番号と owner/repo、親の番号（sub-issue のとき）
- 所見（所見なし入口の 2 周目以降は、直前の issue-reviewer の「直し方」）
- 前の周で直した内容の要約
- scratchpad の絶対パス
- 「CLOSED の issue（配下・親を含む）は直さないこと。直す必要があれば『再判定に回す issue』に挙げて返すこと」

返答の「段」で分ける。

| 段 | すること |
| --- | --- |
| design-doc（「人に聞く」） | **止める。** 書き換えられていない。「人に聞く」をそのまま報告に載せる |
| tech-requirements ／ issue のみ | 手順 3 へ。「tech-requirements.md のずれ」があれば報告に載せる（ファイルは fixer が直さず、implementer が直す） |

### 3. issue-reviewer で判定する

Agent tool で `subagent_type: issue-reviewer`。**並列に回さない。** 1 本ずつ、前の判定と直しを prompt に入れる。

見る範囲は、直した issue の配下の sub-issue 全部と、その親。**fixer が親を直したなら、親と全 sub-issue。** 所見なし入口の最初の判定は、渡された issue（親なら親と全 sub-issue）を見る。順は、親の「やること」に書かれた順を採り、GitHub の並びと違えば報告に書く。

prompt には次を入れる。

- issue 番号と owner/repo
- 役割（`単独` ／ `親` ／ `sub-issue`。sub-issue なら親の番号）
- 直前に直した issue と「何をどう直したか」（判定の前提が動いているため）
- 「issue を書き換えないこと。判定と直し方だけを返すこと」

判定で分ける。

| 判定 | すること |
| --- | --- |
| 妥当 | 直さない。形の指摘だけが残ったなら、それも直さず報告に書く |
| 直しが要る | OPEN なら手順 4 へ。CLOSED なら直さず、所見と直し方を報告に残す |
| 目的から見直し | **直さず、そこで止める。** 食い違いを reviewer の文のまま人に返す |

**大きさは判定とは別に扱う。** 大きすぎ・小さすぎと分け方・まとめ方の案は本文に当てず、報告に載せて人に返す。所見なし入口では、これが出たら止める。

### 4. 周回する。上限 3 周

「直しが要る」が 1 本でもあれば、**同じ issue-fixer に SendMessage** で、その issue の番号と reviewer の「直し方」を渡して直させる（fixer が居なければ新しく立て、prompt に前回の所見と直し方を入れる）。直ったら手順 3 に戻る（周回 +1）。

- 1 周 = fixer が直す → reviewer が見る範囲を判定する、の 1 往復。所見なし入口の最初の判定は 0 周目で、直しが要るときだけ 1 周目の fixer に進む
- **全 issue が妥当** になったら終わり
- **3 周目の判定でも「直しが要る」** なら、issue は直したまま止める。残った所見を報告に載せる
- 「人に聞く」「目的から見直し」、所見なし入口での大きさの指摘は、周回に入れず止めて人に返す

### 5. 報告する

周回数と、issue ごとに 1 行の表。

```
| issue | 役割 | 判定（周ごと） | 大きさ | 直したか | 主な所見 |
```

続けて、止めた理由（人に聞く・目的から見直し・大きさ・3 周・CLOSED）と、残った所見、tech-requirements.md のずれを書く。大きすぎ・小さすぎは分け方・まとめ方の案を載せ、本文は直していないと明記する。

## 守ること

- subagent は 1 本ずつ。並列に回さない
- 本文・タイトル・コメント・sub-issue の追加と close を書くのは issue-fixer だけ。回す側と issue-reviewer は書かない
- 直すのは所見の範囲だけ。文体や語の好みで直さない
- 「人に聞く」「目的から見直し」は人に返す。目的や合意を変えるのは人の判断
- subagent の返答に「読めなかった」とあれば、読めなかった物を報告に書く。読めていない判定で直さない
