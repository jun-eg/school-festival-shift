# 技術の要件定義（Tech Requirements）

> Design Doc が確定させた判断を受け、**「システムが何を達成する必要があるか」**に翻訳する。

アイデア出しフレームワーク 3 ステップの**次に来る 1 本**。フレームワークの中には入らない。

```
ユーザージャーニーマップ  →  HMW  →  Design Doc  →  【技術の要件定義】  →  実装
```

- **入力**: `docs/design-doc.md`（**ステータスが Fixed のもの**。特に機能要件とマイルストーン）、
  機能要件が名指ししている**一次記録**（記録・記録から出力したデータ・既存の設定の実体）
- **出力**: `docs/tech-requirements.md` — **1 本**
- **雛形**: `docs/tech-requirements-template.md` をコピーして書き始める

入力の Design Doc が無い、または**ステータスが Draft のまま**なら、**ここから始めない**。先に `design-doc` skill を回して確定させる。
Draft のまま技術に降りると、Design Doc 側の判断が動いたときに要件が丸ごと作り直しになる。

## この文書は何を持つのか

**Design Doc は「ソフトウェアの仕様書・設計書とは別物」と自分で書いている。** この文書がその受け皿である。
読者は**実装する人・レビューする人・完了を判定する人**。

役目は 3 つ。

1. **翻訳** — 合意された価値と判断を、実装できる要件に置き換える
2. **原本** — 記録から写した定義（項目・形式の実体・件数）の置き場になる。**上流に置くと冗長で、すぐ腐る**
3. **判定** — 完了を「**誰が何を数えて決めるか**」まで降ろす

### この文書を起こさない場合

**すべての取り組みが必要とするわけではない。** 複雑さ・不確実性・落としたときの損失が小さいなら、起こさない判断でよい。

**ただし、Design Doc に「項目の表」「形式の実体」「件数」「規則の展開手順」が書き足され始めたら、それが起こすサインである。**
器が無いと溜まる先が上流しかなく、Design Doc が設計書になっていく。

## Design Doc との境界

**これがこの skill の本体である。** 「何がこちらに来て、何が上流に残るか」が決まっていないと、次の題材でまた同じ溜まり方をする。

### 境界の判定 — 「合意が動くか」

ある 1 行をどちらに書くかは、次の 1 問で決まる。

> **それを覆すと、関係者の合意が動くか。**

- **動く → 判断。** Design Doc に残る
- **動かない（実現手段・値・形式だけが変わる）→ 仕様。** この文書に来る

**迷ったら、覆す場面を実際に想像する。** 「これを変えるには誰に断りが要るか」に名前が出てくるなら判断、
「実装者が直して終わり」なら仕様である。

### 5 つの分かれ目

| 分かれ目 | Design Doc に残るもの | この文書に来るもの |
| --- | --- | --- |
| **業務の規則** | 規則を**どう扱うと決めたか**（特別扱いを設ける・決まらないものは人に返す） | 規則を**機械が適用できる形**（適用の順序・網羅・境界値） |
| **記録からの転記** | **何を転記元にしたか**と、**変えないという判断** | **在処と、変えないという判断**（上流と同じ行を、実体に寄せて持ち直す）。**実体そのもの**（項目の表・形式の実体・件数）**の原本は、記録がリポジトリに入っているなら記録の隣、入っていないならこの文書**（→ 2） |
| **判断と、その帰結の仕様** | **なぜその形か**。トレードオフを検討した選択 | その判断が要求する**観測できる性質** |
| **達成条件・マイルストーン** | **達成条件の数字**と、**日付・完了の定義** | **測り方**（何を数え、どこからが合格か）と、**作業の順序と依存** |
| **△（埋まっていないこと）** | **判断が決まっていない** △ | **判断は決まっているが、値・形式・手段が決まっていない** △ |

以下、1 つずつ。

### 1. 業務の規則 — **発明を禁止すれば、送れる**

業務の規則は、**関係者の頭の中にあって、実装手段ではないもの**である。だから「技術に送ると、規則そのものが技術側で発明される」という不安が立つ。
**その不安はこの 3 つで解消する。** 解消したうえで、規則の**適用形**はこちらに来る。

1. **この文書は規則を発明しない。** 書ける規則は**出どころを持つものだけ**
   （一次記録 ／ 関係者の証言 ／ Design Doc が確定させた判断）
2. **出どころの無い規則は書かない。** 書きたくなったら **△ に置いて Design Doc に返す**。
   「とりあえず妥当な形」で埋めた瞬間に、発明が起きている
3. **規則を「こう扱う」と決める判断は、こちらでしない。** 特別扱いを設けるか、端をどう切るか、
   決まらないものを人に返すか — これは合意が動くので Design Doc の仕事

**判定は 1 問。** その 1 行を関係者に読み上げたとき、

- **「そうです」か「違います」が返る → 規則。** 出どころが必須
- **「どちらでもいい」が返る → 実装。** 出どころは不要で、選定理由が要る

**規則の実体（適用の順序・網羅・境界値）は、こちらが原本になる。**
上流には「その規則があるという事実」と「どう扱うと決めたか」だけが残る。

### 2. 記録からの転記 — **判断はこちら。実体は記録の隣**

**転記は判断ではない。** 覆しても合意は動かないので、**上流には残らない。**
上流に残るのは「何を転記元にしたか」と「**変えないという判断**」の行だけである。

- **正式な定義（項目の一覧・形式の実体・データの件数）を上流にコピペしない。** 冗長で、すぐ腐る
- **写す。揃えない・直さない。** 表記の揺れ・不整合も**そのまま写す**。
  揃えるのは「**変える判断**」であって、転記ではない。揃えたいなら Design Doc に戻して判断を起こす
- **転記した行には在処を添える**（どのファイル・どの記録の、どこか）。在処の無い転記は、次に読む人が突き合わせられない
- **転記元が読めなかったところは、埋めずに △ にする**

**実体の原本を、どこに置くか。** **記録そのものがリポジトリに入っているかで分かれる。**

| 記録がリポジトリに | 実体の原本 | この文書が持つもの |
| --- | --- | --- |
| **入っていない** | **この文書。**ほかに置き場が無い | **在処 ＋ 変えないという判断 ＋ 実体** |
| **入っている** | **記録の隣**（記録と同じディレクトリに 1 本） | **在処 ＋ 変えないという判断だけ** |

**記録が後から入ってきたら、実体を記録の隣へ出す。** **入った時点で前提が変わっている** —
「置き場が無いからこちらが原本」だった理由が消えるからである。**出すなら、出す前に ADR を起こす**（手順の「上流を 1 行ずつ仕分ける」の**上流から実体を抜くなら**と同じ扱い。**動くのは原本の持ち主であって、判定ではない**）。

**分かれ目は「`ls` で突き合わせられるか」である。**

- **記録を見れば確かめられる文**（件数・項目の一覧・揃っていないところ・突き合わせ）→ **記録の隣**
- **記録の来歴**（別の転記元から起こしたものとの差など、**機械では出ないもの**）→ **記録の隣**
- **「こう扱うと決めた」文**（揃えない・振り直さない・畳まない・数えない・型に乗らない・妥当性に使わない）→ **この文書**

**実体が膨らむのは、記録を引き直したときである。** **これは上流のスコープが広がったサインではないので、
上流に戻しても減らない**（→「この文書は 1 本にする」の分岐）。

#### この文書の成長の不変量

**記録を 1 回引き直したとき、この文書に増えるのは在処と「変えないという判断」の行だけ**（数行）**である。**
**項目の一覧・形式の実体・件数・揃っていないところは 0 行** — 増えるのは**記録の隣**である。

**ここが 100 行単位で伸びたら、実体を持ち込んでいる。** 上の表の「入っている」側なのに実体がこちらにあるか、
**実体を出したあとも在処の行に件数を書き足しているかのどちらかである。**

**ただし、記録がリポジトリに入っていないなら伸びてよい**（上の表の「入っていない」側）。
**そのときの不変量はこちらではなく「入ってきたら出す」のほうである。**

### 3. 判断と、その帰結の仕様

- **判断** = なぜその形にするのか。他の形を検討したうえでの選択。**Design Doc**
- **仕様** = その判断が要求する、**観測できる性質**。**この文書**

**仕様は、判断の言い換えではない。** 「〜を満たす」ではなく、**何を見れば満たしたと分かるか**の文にする。
判定者の居ない要件は要件ではない。

**この文書が判断を新しく作らない。** 書いていて判断が必要になったら、**上流に戻して起こす。**
**この文書が Design Doc を上書きする形にしない。**

- Design Doc の**対象外を広げない。** 技術が決まっても、対象外に置いたものは戻ってこない
- **この文書で新しく足した対象外は、明記して合意する。** 「対象外」の解釈違いは手戻りになる。
  足した対象外に、この文書の要件が**依存していないか**も見る

### 4. 達成条件・マイルストーン

**どちらも完了判定に使うものなので、二重に持つと片方が腐る。** 持ち主を分ける。

- **達成条件**: **数字は上流のもの。** この文書は**測り方**を持つ
  （何を入力に、何を数え、どこからが合格か、**誰が測るか**）。**数字を書き換えない。**
  測ってみて届かなかったときは、達成条件を動かす前に**内訳（△）を見る**。動かすなら上流の判定を動かす
- **マイルストーン**: **日付と完了の定義は上流のもの。** この文書は**技術的な作業の順序と依存**を持つ。
  **日付を写さない。** 写した日付は上流が動いたときに必ず取り残される。
  上流のマイルストーンは**完了の定義の番号で指す**

### 5. △（埋まっていないこと）

- **判断が決まっていない** → **Design Doc の △**
- **判断は決まっているが、値・形式・手段が決まっていない** → **この文書の △**
- **この文書で新しく見つけた △ が上流の判断に効くなら、上流に送る**（ADR を 1 本起こし、上流の更新ログに 1 行足す）
- 1 行は**何が決まっていないか ＋ 何が分かれば決まるか**
- **△ が 1 つも無いなら「現時点で △ は無い」と 1 行書く。節ごと消さない。**
  消すと、洗い出したうえで無かったのか、洗い出していないのかが区別できない

## 記号（◎ / ○ / △）と出どころを落とさない

**上流が記号で持っている主張は、こちらでも記号で持つ。** 落とすと**裏付けの限界が消える**。
記号の無い要件は、裏が取れているのか決めただけなのかが読み手に区別できない。

**この文書の主張は 3 種類あり、記号の付け方が違う。**

| 主張の種類 | 記号 | 添えるもの |
| --- | --- | --- |
| **上流・記録から引いたもの** | 引いた記号と (n/m) を**そのまま** | 引用元（上流の節番号・項目番号） |
| **記録からの転記** | **（記録）** | 一次記録の在処 |
| **この文書で新しく決めた選定** | **付けない** | **選定理由と、却下した選択肢** |

- **技術選定に ◎ を付けない。** ◎ は「観測して裏が取れた」の意味で、**選定は観測ではない**。
  付けると、裏付けのある主張と決めたことの区別が消える
- **記号の付いていない主張を、上流から引いたことにしない**
- 記号と (n/m) の規約の原本は
  [`.claude/skills/user-journey-map/references/evidence.md`](../user-journey-map/references/evidence.md)。**書き写さない**

## 手順

### 1. 入力を揃える

書き始める前に手元に置く。無いまま埋めにいかない。

- `docs/design-doc.md` — **ステータスが Fixed であること**。機能要件（スコープ内・対象外・△）とマイルストーン
- 機能要件が名指ししている**一次記録**。転記の元になる
- 完了判定に使う**入力データ**が手元にあるか。無いなら、それ自体が △ である

### 2. 雛形をコピーする

`docs/tech-requirements-template.md` を `docs/tech-requirements.md` にコピーし、
ガイドの引用ブロック（`>` で始まる部分）を読みながら埋める。埋めたガイドは消してよい。

### 3. 上流を 1 行ずつ仕分ける

**上流の機能要件とマイルストーンを 1 行ずつ読み、「合意が動くか」で仕分ける。**

- **仕分けの結果を、この文書の「入力元」の表に残す。** 残さないと、次に読む人が同じ仕分けをやり直す
- **上流のスコープ内の項目を、1 つも取りこぼさない。** 対応する要件が無い項目が残っていないかを数える
- **上流から実体を抜くなら、抜く前に ADR を起こす**（規約は [`docs/ADR/README.md`](../../../docs/ADR/README.md)）。
  先に抜くと、抜いた瞬間に情報が消える
- **この文書から実体を抜くときも同じである**（記録の実体を記録の隣に出す場合 → 「記録からの転記」）
- **抜かずに両方に持たない。** どちらが原本か分からなくなる

### 4. 規則と転記を先に埋める

**選定より先に、入力として受けるものを固める。** ここが動くと選定が全部やり直しになる。

- 業務の規則 — **出どころ付き**で。出どころが無いものは △
- 記録からの転記 — **揺れを含めてそのまま**。在処を添える

### 5. 実行形態と前提を決める — **一番きつい制約から**

**実行形態は選定の 1 つだが、他の選定を全部縛るので先に置く。**

- **動かす相手は誰で、その人に何を要求してよいか。** 前提知識が振れるなら、**振れ幅の下側で成立するか**を見る
- **セットアップに要求するものを名指しする。** 要求した時点で止まる人が居るなら、それは達成条件に反する
- **「止まったら失敗である」と上流が書いているなら、止まる箇所を先に洗う**

### 6. 仕様を書く

**判定できる文にする。** 何を見れば満たしたと分かるかを書く。上流の判断ごとに、帰結の仕様を並べる。

### 7. 検証の側を、作る側と並べて書く

**完了の判定には「違反を数える側」が要る。作る側より先に決める。** 無いと完了判定そのものができない。

- 何を違反と数えるか。**0 でなければ未達なのか、名指しで残ればよいのか**
- **判定に使う入力データを加工して置くなら、加工しても保つものを名指しする。**
  **形式だけでは足りない** — 項目をまたぐ関係と件数が落ちると、そこが検証対象だったときに判定が成立しない。
  **記録が黙っている点をこちらで決めたなら、その帰結（何が検証できなくなるか）を書く**
- 加工の順序も決める。**元のデータを一度でも記録に残すと、消しても戻せない**
- **確かめたことを、断定だけで置かない。** 「全件再現している」「重なっているものは無い」と書くなら、
  **どのファイルを・どう数えた結果か**を添える。**数え方があれば、次に読む人が数え直せる。**
  **散文の断定は、数えれば出る誤りでもレビューを通る**
- **宣言しないと数えられないものがある。** **畳み方**（重複した行のどれを採るか）・
  **重なりの定義**（端が接するだけを重なりに数えるか）・**一致の定義**（何と何を比べ、形が崩れた行をどう扱うか）。
  **決めた側を書く。**書かないと、同じデータから別の数が出る

### 8. 作業の順序を書く

**動くものが出てくる順**に並べ、依存を書く。**日付は書かない**（上流が持つ）。

### 9. △ を残して、読み返す

下の観点で読み返す。引っかかったら該当セクションに戻る。

## レビュー観点

### 1. 上流の判断を、この文書の中で動かしていないか

動かしたくなったら、**ADR を 1 本起こして上流の更新ログに 1 行足す。**
この文書の中で静かに上書きすると、合意を取った文書と実装が食い違ったまま進む。

### 2. 出どころの無い規則が紛れていないか

**「妥当だから」で書いた規則は発明である。** 出どころを 1 つずつ指せるかを見る。

### 3. 選定に記号が付いていないか

◎ の付いた技術選定は、**裏付けがあるように見えて無い**。理由とトレードオフに書き換える。

### 4. 仕様が「判定できる文」になっているか

「〜を考慮する」「〜に配慮する」は判定できない。**誰が何を見て決めるか**まで降ろす。

### 5. 対象外に置いたものに、要件が依存していないか

**「今回やらない」と「それが無い状態に依存する」は別である。**

## 成果物のフォーマット

**原本は [`docs/tech-requirements-template.md`](../../../docs/tech-requirements-template.md) 1 つ。**
**ここに雛形を書き写さない。**

```markdown
# 技術の要件定義: <取り組みの名前>

## 入力元（上流の何を受けたか）

## 1. Overview（この文書が引き受ける範囲）
## 2. 実行形態と前提
## 3. 業務の規則
## 4. 記録からの転記
## 5. 仕様
## 6. 技術選定とトレードオフ
## 7. 検証と完了の測り方
## 8. 作業の順序
## 9. 埋まっていないこと（△）

## 更新ログ
```

**この文書は 1 本にする。** 機能ごとに分けない。
実行形態（2）・検証（7）・完了の測り方は機能をまたぐので、分けると各本に重複して写る。
写った時点で、**どちらが原本か分からなくなる**。

**「どこまでで完了か」の判定単位を文書の外に出さない**のが 1 本にする理由である。

機能ごとの粒度は 5. 仕様の中で扱う。

### 1 本に収まらないほど大きいと感じたら

**大きさだけで 1 つの結論に飛ばさない。** **まず「どの節が伸びたか」を数える。**

| 何が伸びたか | 何のサインか | どうするか |
| --- | --- | --- |
| **仕様（判断の帰結）** — 5・6 | **上流のスコープが広すぎる** | **上流に戻す**（Design Doc の 6 のスコープを絞る） |
| **記録の実体** — 4・7 の転記・件数・揃っていないところ | **器が無い。**上流に戻しても減らない | **器を分ける**（実体を記録の隣に出す → 2） |

**見分けは、上流の側で付く。** **この文書だけが伸びていて、上流の「引き受ける範囲」が動いていないなら、
伸びたのは仕様ではない。** スコープが広がっていないものを上流に戻しても、**戻す先が無い。**

**どちらでも文書は割らない。** **器を分けることと、機能で割ることは別である** —
**割ってはいけないのは「どこまでで完了か」の判定単位**であって、**実体の置き場ではない。**
**判断がこの文書に残っているかぎり、1 本のままである**（→ 2）。

### 更新ログ節

**末尾の `## 更新ログ` は、この文書の判定が動いたときの索引**
（選定が覆った・仕様が変わった・測り方が変わった・△ が増減した）。
`docs/tech-requirements.md` を起こした時点では ADR が 0 本なので、**見出しと空の表だけ置く**。
判定が動いたら ADR を 1 本起こし、ここに **1 行（日付・動いたもの・ADR へのリンク）**足す。
**ここに理由・経緯を書き始めたら、それは ADR に書くもの。**

**上流の判断が動いた場合は、こちらではなく `docs/ADR/design-doc/` と Design Doc の更新ログに足す。**
**1 つの判定を両方に二重に書かない。**

置き場所（`docs/ADR/tech-requirements/`）・フォルダを作るタイミング・ファイル名・連番・Status・参照の書き方は
[`docs/ADR/README.md`](../../../docs/ADR/README.md)、雛形は [`docs/ADR/_template.md`](../../../docs/ADR/_template.md)。
**規約をここに書き写さない。**
