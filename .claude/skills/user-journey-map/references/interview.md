# ユーザーインタビュー

ジャーニーマップの**精度を上げる手段**。マップを書く → 解像度が荒い部分を洗い出す → **ここで聞く** → マップに肉付けする、という流れで使う。

Design Doc の User Story を書くときの一次情報としても参照する。

## 意義

- **定性的な一次情報が得られる** — 数値では出てこない「なぜ」が分かる
- **仮説を検証できる** — 想像で埋めた部分が合っていたか確かめられる
- **ニーズのズレを防ぐ** — 作り手が思う課題と、実際の課題のズレを早期に潰せる
- **5〜6 人で十分** — それ以降は新しい発見が得られにくい。人数を増やすより深掘りに時間を使う

## 目的は 2 つ

1. **ニーズの把握** — 何に困っているのか
2. **ソリューションの改善** — 考えている案が本当に効くのか

どちらを聞きに行くのかを、インタビュー前に決めておく。

## 質問リスト

### 1. 背景・状況

- 普段どのように〇〇に関わっていますか
- どのくらいの頻度でやっていますか
- 直近で困った・迷った経験はありますか

### 2. 具体的な行動

- 直近で〇〇したときのことを教えてください
- 最初に何をしましたか？ その次は？
- 他に検討した選択肢はありましたか？ なぜそれを選ばなかったのですか？

### 3. 判断・感情・価値観

- 何が決め手でしたか
- 一番大変だったのはどこですか
- 理想の状態はどんな状態ですか

### 4. まとめ

- 一番課題だと感じている点はどこですか
- 言い残したことはありますか

## 深掘りのコツ

そのまま使える言い回し:

- 「もう少し詳しく教えてください」
- 「具体的にはどういうことですか？」
- 「なぜそう思われたのですか？」

**意見より、過去の実際の行動・エピソードを聞く。** 「どう思いますか」への答えはその場で作られた意見だが、「前回どうしましたか」への答えは実際に起きたことなので、信頼できるデータになる。

## 避けること

- **誘導質問** — 「〇〇が不便ですよね？」のように、答えを含んだ聞き方をしない
- **否定的な聞き方** — ×「なぜ使わないんですか」 / ○「どんなときに使わないと思いますか」
- **いきなり核心を聞く** — **事実 → 判断 → 感情 → 背景**の順で近づく。最初から「一番の課題は何ですか」と聞いても、本人が言語化できていないことが多い

## 終わったら

聞いた内容を `docs/user-journey-map.md` のジャーニーマップに反映する。

- 想像で埋めていた箇所を、実際の証言で置き換える
- 新しく出てきたペインポイントを TASK LIST / FEELING ADJECTIVE に追加する
- 裏が取れた部分と、まだ想像のままの部分を区別できるようにしておく
