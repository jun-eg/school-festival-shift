# ユーザージャーニーマップ

> 『ユーザが特定のゴールを達成するまでの一連の体験』を可視化する。

アイデア出しフレームワーク 3 ステップの **1 つ目**。

```
【ユーザージャーニーマップ】  →  HMW  →  Design Doc
```

- **入力**: なし（ここが起点）
- **出力**: **立場ごとに 1 本のマップ** — `docs/journey/<立場>.md`。各本が改善機会のリスト ＋ 確定したペルソナを持つ（HMW と Design Doc の入力になる）

## なぜこの工程をスキップしないのか

1. **障害物のない道筋を作る** — 目的までのルート上にある障害を先に可視化する
2. **バイアスの影響を軽減する** — 自分の感覚ではなく、第三者の視点でプロセスを見る
3. **新たなペインポイントを浮き彫りにする** — 具体的な行動をイメージし直すことで、最初は見えなかった課題が出てくる

## 手順

### 0. ペルソナを確定する

**未確定のまま先へ進まない。** ここが曖昧だと以降の 4 列すべてが曖昧になる。

- 「ユーザー」ではなく**具体的な個人**（仮想の特定人物）を設定する
- 立場が複数ある場合（例: 作る人 / 使う人）は、**この 1 本をどちらか 1 人に決める**。両方書くと体験が混ざって改善機会がぼやける
- **もう一方の立場は、別ファイルでもう 1 本起こす。** 切り捨てるわけではない（→「マップは立場ごとに 1 本」）
- 最低限これを埋める: 名前 / 属性・所属 / ゴール / 前提知識・スキル / 置かれている制約

ユーザーに確認せずに勝手に決めない。候補が複数あるなら選択肢として提示して確定させる。

#### マップは立場ごとに 1 本

**1 本のマップに 2 つの立場を入れない。** ACTION は時系列の区切りなので、
立場が違えば時系列そのものが別物になる（作る側の「希望収集フォームを*作る*」と
入る側の「希望を*出す*」は、同じ時期に起きる**別の ACTION**）。
片方のセルにもう片方の体験を差し込むと、そのセルだけが膨らみ、
**間借りしている側のジャーニーは時系列として存在しないまま**になる。

| | |
| --- | --- |
| 1 ファイル | 1 立場 = 1 ペルソナ = 1 本のジャーニー |
| パス | `docs/journey/<立場>.md`（例: `docs/journey/作る側.md`、`docs/journey/入る側.md`） |
| 連番は付けない | 立場は少数で作成順に意味がない。`docs/interviews/<連番>-<立場>.md` の連番は**インタビューの実施順**であり、意味が違うので番号を揃えない |

**分ける単位は「立場」であって「証言者」ではない。** ペルソナは証言者そのものではなく、
**複数の証言から合成した 1 人**。同じ立場・同じゴールなら、学年や役職の違いは
1 つのペルソナ内のばらつきとして扱う。証言者ごとに 1 本にすると、
人を増やすたびにマップが増えて**それは逐語になる**。

#### 1 人が 2 つの立場を兼ねているとき

**人ではなく、語った体験で振り分ける。**（作る側の担当者が自分でもシフトに入る、など）

- その人が**作る側として語った体験**は作る側のマップ、**入る側として語った体験**は入る側のマップへ
- **1 人の証言が 2 本に寄与してよい。** 兼務は隠さず、各マップの証言者表に「○○も兼ねる」と書く
- (n/m) の**母数はその立場について聞いた人数**にする。作る側 1 人・入る側 2 人に聞いて
  そのうち 1 人が兼務なら、入る側のマップでは (n/3) になる

### 1. ACTION

**1 回に 1 つのアクション**を書く。ゴールに向かう時系列の区切りになる。

- 動詞で書く（「募集を告知する」「希望を集める」「割り当てる」）
- 粒度を揃える。1 つの ACTION に複数の目的が入っていたら分割する

### 2. TASK LIST

その ACTION のためにユーザーが実際にやることを**すべて**リストアップする。

- 「すべて」が重要。省略した先に課題が潜んでいることが多い
- 頭の中でやっている判断・確認・待ち時間も書く

### 3. FEELING ADJECTIVE

**タスクからタスクへ移動するときの感情を形容詞で**特定する。

- 形容詞で書く（「面倒」「不安」「億劫」「ほっとする」）。文章にしない
- ポジティブ／ネガティブの両方を書く。ネガティブが集中している箇所が改善機会の候補

### 4. IMPROVEMENT OPPORTUNITIES

ユーザー体験を向上させる**機会**を特定する。

- **解決策ではなく「機会」**を書く。ここで実装案に飛びつかない（それは後工程の仕事）
- ネガティブな FEELING と、TASK LIST の中の手作業・待ち・二重確認に紐づけて書く

### 5. 解像度が荒い部分を洗い出す

書いていて「分からなかった」「想像で埋めた」部分を、そのままインタビュー項目として書き留める。
**ここと「未検証（△）」節が Interview List を兼ねる**ので、専用の置き場所は作らない。

→ **聞きに行く前に `interview-questions` skill を呼ぶ**（`/interview-questions`）。
この節と △ / ○ を入力として、相手 1 人分のインタビューガイドを `docs/interviews/` に出す。
**入力に使うのは、その相手の立場のマップ**（入る側に聞くなら `docs/journey/入る側.md` の △ / ○）。
まだその立場のマップが無いなら、**先にその立場の 1 本を起こしてから**質問を組む。
「どう聞くか」（深掘り・誘導質問の回避・避けること）は
`.claude/skills/interview-questions/references/interview.md` が持つ。

### 6. インタビュー後に肉付けする

**生の回答は `docs/interviews/<連番>-<相手の立場>.md` の「回答」節に追記する**（ガイドを出したのと同じファイル）。
**マップには逐語を置かない。** 同じ回答が 2 か所に増えて、どちらが原本か分からなくなる。

そのうえで、読み取った結論でマップを更新する。想像で埋めた箇所を実際の証言で置き換え、
**新しく出てきたペインポイントを追加する**。

**戻す先は、その証言が語っている立場のマップ。** 入る側の証言を作る側のマップのセルに
差し込まない（手順 0 の「マップは立場ごとに 1 本」が壊れる）。
戻す先のマップがまだ無ければ**その立場の 1 本を新しく起こす**。既存のマップに間借りさせない。
1 人が 2 つの立場を兼ねているときの振り分けも手順 0 に従う。

- マップ内では、**想像で埋めた部分と、インタビューで裏が取れた部分を区別できるようにしておく**（出典を書く等）
- **出典の記号を立場ごとに分けない。** 1 本 = 1 立場なので、そのマップの ◎ はその立場の証言を指す。
  立場を区別する記号（◎作 / ◎入 のような枝分かれ）が要るなら、それは**マップが混ざっているサイン**
- **1 人の証言を全員の話にしない。** 何人中何人が言ったかを (n/m) で添える（母数はその立場について聞いた人数）
- ガイド側の対応表の**該当／非該当を数えて埋める**のもこの手順（器は `interview-questions` が用意している）

| どこに | 何を |
| --- | --- |
| `docs/interviews/<連番>-<立場>.md` | **一次情報** — 誰が何と答えたか |
| `docs/journey/<立場>.md` | **結論** — その立場について読み取ったことと、◎ / ○ / △ の記号 |

### 7. 改善機会リストを書き出す

**マップ 1 本ごとに**、そのファイルの末尾に改善機会を**箇条書き**で抽出する。

**ここが空だと後工程（HMW）が止まる。** 必ず埋める。

**統合したリストは別ファイルにしない。** HMW は `docs/journey/` にある**全マップの改善機会リストを
1 つの候補プール**として見て、そこから 1 つ選ぶ。まとめ直したファイルを作ると原本が二重化して、
どちらが最新か分からなくなる。

## 成果物のフォーマット

**立場 1 つにつき 1 ファイル**、`docs/journey/<立場>.md` に以下を書く。

```markdown
# ユーザージャーニーマップ — <立場>

## 証言者
この立場について誰に聞いたか（他の立場と兼務している人はその旨も）

## ペルソナ
名前 / 属性 / ゴール / 前提知識 / 制約（**このファイルにつき 1 人**）

## ジャーニーマップ

| ACTION | TASK LIST | FEELING ADJECTIVE | IMPROVEMENT OPPORTUNITIES |
| --- | --- | --- | --- |
| ... | ... | ... | ... |

## 解像度が荒い部分（インタビューで聞く）
- ...

## 改善機会リスト
- ...
```

## 完了チェック

- [ ] **このマップが扱う立場が 1 つ**に決まっていて、ファイル名が `docs/journey/<立場>.md` になっている
- [ ] ペルソナが**このマップにつき 1 人分**、具体的な個人として確定している
- [ ] 他の立場の体験が ACTION のセルに間借りしていない（していたら、その立場のマップを別に起こす）
- [ ] ACTION が時系列に並び、粒度が揃っている
- [ ] TASK LIST に「頭の中の作業」も含めて**すべて**書かれている
- [ ] FEELING ADJECTIVE が**形容詞**で書かれている
- [ ] IMPROVEMENT OPPORTUNITIES が解決策ではなく**機会**として書かれている
- [ ] 解像度が荒い部分がインタビュー項目として残っている（`interview-questions` skill の入力になる）
- [ ] 改善機会が箇条書きで抽出されている（**空にしない**）
- [ ] 立場が複数あるなら、**それぞれの立場のマップが `docs/journey/` に揃っている**
