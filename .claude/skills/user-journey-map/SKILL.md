# ユーザージャーニーマップ

> 『ユーザが特定のゴールを達成するまでの一連の体験』を可視化する。

アイデア出しフレームワーク 3 ステップの **1 つ目**。

```
【ユーザージャーニーマップ】  →  HMW  →  Design Doc
```

- **入力**: なし（ここが起点）
- **出力**: **立場ごとに 1 本のマップ** — `docs/journey/<立場>.md`。各本が改善機会のリスト ＋ 確定したペルソナを持つ（HMW と Design Doc の入力になる）

## 参照

| ファイル | 何を持つ |
| --- | --- |
| [`references/evidence.md`](references/evidence.md) | **出典記号（◎ / ○ / △ /（記録））と (n/m) の数え方。** マップ側に書き写さない |
| [`docs/ADR/README.md`](../../../docs/ADR/README.md) | **判定が動いた記録の置き場所と規約。** 本文には残さない |
| [`docs/journey/_template.md`](../../../docs/journey/_template.md) | **節構成の原本。** マップはこれをコピーして起こす |

## なぜこの工程をスキップしないのか

1. **障害物のない道筋を作る** — 目的までのルート上にある障害を先に可視化する
2. **バイアスの影響を軽減する** — 自分の感覚ではなく、第三者の視点でプロセスを見る
3. **新たなペインポイントを浮き彫りにする** — 具体的な行動をイメージし直すことで、最初は見えなかった課題が出てくる

## 手順

### 0. ペルソナを確定する

**未確定のまま先へ進まない。** ここが曖昧だと以降の 4 列すべてが曖昧になる。

- 「ユーザー」ではなく**具体的な個人**（仮想の特定人物）を設定する
- 立場が複数ある場合（例: 作る人 / 使う人）は、**この 1 本をどちらか 1 人に決める**。両方書くと体験が混ざって改善機会がぼやける
- **もう一方の立場は、別ファイルでもう 1 本起こす。** 切り捨てるわけではない（→「マップは立場ごとに 1 本」）
- 最低限これを埋める: 名前 / 属性・所属 / ゴール / 前提知識・スキル / 置かれている制約

ユーザーに確認せずに勝手に決めない。候補が複数あるなら選択肢として提示して確定させる。

#### マップは立場ごとに 1 本

**1 本のマップに 2 つの立場を入れない。** ACTION は時系列の区切りなので、
立場が違えば時系列そのものが別物になる（作る側の「希望収集フォームを*作る*」と
入る側の「希望を*出す*」は、同じ時期に起きる**別の ACTION**）。
片方のセルにもう片方の体験を差し込むと、そのセルだけが膨らみ、
**間借りしている側のジャーニーは時系列として存在しないまま**になる。

| | |
| --- | --- |
| 1 ファイル | 1 立場 = 1 ペルソナ = 1 本のジャーニー |
| パス | `docs/journey/<立場>.md`（例: `docs/journey/作る側.md`、`docs/journey/入る側.md`） |
| 連番は付けない | 立場は少数で作成順に意味がない。`docs/interviews/<連番>-<立場>.md` の連番は**インタビューの実施順**であり、意味が違うので番号を揃えない |

**分ける単位は「立場」であって「証言者」ではない。** ペルソナは証言者そのものではなく、
**複数の証言から合成した 1 人**。同じ立場・同じゴールなら、学年や役職の違いは
1 つのペルソナ内のばらつきとして扱う。証言者ごとに 1 本にすると、
人を増やすたびにマップが増えて**それは逐語になる**。

#### 1 人が 2 つの立場を兼ねているとき

**人ではなく、語った体験で振り分ける。**（作る側の担当者が自分でもシフトに入る、など）

- その人が**作る側として語った体験**は作る側のマップ、**入る側として語った体験**は入る側のマップへ
- **1 人の証言が 2 本に寄与してよい。** 兼務は隠さず、各マップの証言者表に「○○も兼ねる」と書く
- (n/m) の**母数はその立場について聞いた人数**にする。作る側 1 人・入る側 2 人に聞いて
  そのうち 1 人が兼務なら、入る側のマップでは (n/3) になる

### 1. ACTION

**1 回に 1 つのアクション**を書く。ゴールに向かう時系列の区切りになる。

- 動詞で書く（「募集を告知する」「希望を集める」「割り当てる」）
- 粒度を揃える。1 つの ACTION に複数の目的が入っていたら分割する

### 2. TASK LIST

その ACTION のためにユーザーが実際にやることを**すべて**リストアップする。

- 「すべて」が重要。省略した先に課題が潜んでいることが多い
- 頭の中でやっている判断・確認・待ち時間も書く

### 3. FEELING ADJECTIVE

**タスクからタスクへ移動するときの感情を形容詞で**特定する。

- 形容詞で書く（「面倒」「不安」「億劫」「ほっとする」）。文章にしない
- ポジティブ／ネガティブの両方を書く。ネガティブが集中している箇所が改善機会の候補

### 4. IMPROVEMENT OPPORTUNITIES

ユーザー体験を向上させる**機会**を特定する。

- **解決策ではなく「機会」**を書く。ここで実装案に飛びつかない（それは後工程の仕事）
- ネガティブな FEELING と、TASK LIST の中の手作業・待ち・二重確認に紐づけて書く

#### セルは (n/m) のまとめだけを持つ

```
・<まとめ> ◎ (n/m)
　└ ※<人を跨いで言えること。軸と数だけで、人番号は出さない>
```

- **`└ N 人目: <逐語>` を置かない。** 原本は `docs/interviews/<連番>-<立場>.md` の「回答を並べる」表
- 人を跨いだ読み（例:「理由は 3 人で違う」）は**残す** — これは (n/m) から復元できない発見である。
  ただし**中身を 3 つ並べない。「理由は 3 人とも違う」まで**
- **1 人増えたときセルに増えるのは 0 行**（n と m が書き換わるだけ）

### 5. 解像度が荒い部分を洗い出す

書いていて「分からなかった」「想像で埋めた」部分を、そのままインタビュー項目として書き留める。
**ここと「未検証（△）」節が Interview List を兼ねる**ので、専用の置き場所は作らない。

**埋め方がインタビュー以外のもの（記録を引く・突き合わせる）も、同じ節に置く。**
各項目が答えるのは「次に**どうすれば**埋まるか」であって、「次に誰に聞くか」だけではない。
`interview-questions` は「記録」と書かれた行を読み飛ばせばよいので、入力としては壊れない。
**ここで「次のアクション」節を別に立てない** — 聞く宿題と引く宿題が 2 か所に散る。

→ **聞きに行く前に `interview-questions` skill を呼ぶ**（`/interview-questions`）。
この節と △ / ○ を入力として、相手 1 人分のインタビューガイドを `docs/interviews/` に出す。
**入力に使うのは、その相手の立場のマップ**（入る側に聞くなら `docs/journey/入る側.md` の △ / ○）。
まだその立場のマップが無いなら、**先にその立場の 1 本を起こしてから**質問を組む。
「どう聞くか」（深掘り・誘導質問の回避・避けること）は
`.claude/skills/interview-questions/references/interview.md` が持つ。

### 6. インタビュー後に肉付けする

**生の回答は `docs/interviews/<連番>-<相手の立場>.md` の「回答」節に追記する**（ガイドを出したのと同じファイル）。
**マップには逐語を置かない。** 同じ回答が 2 か所に増えて、どちらが原本か分からなくなる。

そのうえで、読み取った結論でマップを更新する。想像で埋めた箇所を実際の証言で置き換え、
**新しく出てきたペインポイントを追加する**。

**戻す先は、その証言が語っている立場のマップ。** 入る側の証言を作る側のマップのセルに
差し込まない（手順 0 の「マップは立場ごとに 1 本」が壊れる）。
戻す先のマップがまだ無ければ**その立場の 1 本を新しく起こす**。既存のマップに間借りさせない。
1 人が 2 つの立場を兼ねているときの振り分けも手順 0 に従う。

- マップ内では、**想像で埋めた部分と、インタビューで裏が取れた部分を区別できるようにしておく**
- **出典記号（◎ / ○ / △ /（記録））と (n/m) の数え方は
  [`references/evidence.md`](references/evidence.md) が持つ。** 母数の決め方・保留の扱い・
  一部の人にしか送っていない問いの数え方・記録と自己申告が食い違ったときの扱いは、すべてそこにある
- **マップ側の「凡例：情報の出典」節にルールを書き写さない。** そこに書くのは
  **そのマップ固有の事実**だけ（母数がいくつか / 実施日 / 逐語がどのファイルにあるか）。
  ルールを写すと、人を 1 人聞くたびに例外が各マップへ 1 行ずつ増える
- ガイド側の対応表の**該当／非該当を数えて埋める**のもこの手順（器は `interview-questions` が用意している）

| どこに | 何を |
| --- | --- |
| `docs/interviews/<連番>-<立場>.md` | **一次情報** — 誰が何と答えたか |
| `docs/journey/<立場>.md` | **結論** — その立場について読み取ったことと、◎ / ○ / △ の記号 |

#### 証言者節は表 1 つに収める

**証言者ごとの小見出しを立てない。** `### N 人目（…）を一般化するときの注意` を人数分並べると、
増え方が **O(人数)** になる。これは「マップには逐語を置かない」を**逐人**の形で破っている
（証言者ごとに 1 本にするのと同じことを、1 本の中でやっている）。

証言者節が持つのは**この 4 つだけ**。

| 器 | 何を持つ | 人が 1 人増えたときに増える量 |
| --- | --- | --- |
| **証言者の表**（`一般化の上限` 列を含む） | 誰に / 実施日 / 母数に数えるか / **その人に付く一般化の上限** | **表の 1 行** |
| **(n/m) の母数の決め方** | この立場で m をいくつにしたか・誰を数えないか | **0 行** |
| **`### 証言を一般化するときの注意`**（単数形） | **標本全体に効く偏りと、当たれていない層** | **0 行**（書き換わるだけ） |
| **`### N 人を並べて言えること`** | 人を跨いで何が揃い、何が割れたか。**軸で持つ** | **0 行**（軸は人数で増えない） |

**マップに写さないもの:**

- **その人が何者か・既存の誰と属性が重なるか** → `docs/interviews/` 側の回答節の小見出しが持つ
  （`interview-questions/SKILL.md` の `<属性。何が散らせて何が重なっているか>`）。
  **「散らせて／重なっている」は一般化の可否そのもの**で、一次情報側が持つと決めてある
- **その人の回答で何が埋まり、何が落ちたか** → 同ファイルの回答表の `埋まったこと／残った空白` 列
- **どちらも移すのではなく消して参照にする。** 移し先に原本があるので、移すと三重化する

**マップ側が持つのは「どこまで一般化してよいか」だけ。** これが journey 側なのは、
**一般化の可否が (n/m) の読み方**だからである。(n/m) は立場についての結論であって個々の回答には付かず、
**一次情報側は m を知らない**。

#### 「一般化の上限」を 2 か所に書かない（→ 手順 7）

| | 何に付く上限か | 器 |
| --- | --- | --- |
| **人**に付く上限 | その人の属性から来る制約（例:「3 属性同居で差分の出どころを切り分け不能」） | **証言者表の `一般化の上限` 列** |
| **項目**に付く上限 | その機会の根拠が (n/m) でどこまで届くか（例:「b を選んだ人は 0 人」） | **改善機会の `注意:` 行**（手順 7） |

**片方をもう片方で言い直さない。** 判定は機械的にできる —
**`注意:` に「N 人目」が出てきたら、それは人に付く上限**で、証言者表の列の言い直しである。

### 6.5. 判定が動いたら ADR を 1 本起こす

**マップ本文は「今の結論」だけを持つ。** 「N 人目まではこうだった → 崩れた」を本文に残すと、
**既存の全項目に 1 段ずつ生える**。これが人を 1 人聞くたびに本文が伸びる主因になる。

かといって経緯は捨てられない。「n=4 で確定と書いたものが n=5 で動いた」は、
次に読む人が **(n/m) をどこまで信用してよいか**を決める材料になる。
git log にはコミットメッセージの粒度しか残らず、**何が何に変わったか・なぜかは追えない**。

| 器 | 何を持つ | 人が 1 人増えたときに増える量 |
| --- | --- | --- |
| マップ本文 | **今の結論だけ** | **0 行**（記号と (n/m) が書き換わるだけ） |
| [`docs/ADR/user-journey-map/`](../../../docs/ADR/README.md) | **判定が動いた記録** | 動いた判定の数だけファイルが増える |
| マップ末尾の「更新ログ」節 | **索引** | 動いた判定の数だけ**行が 1 本ずつ** |

**線引き**: **「(n/m) がいくつか」は結論なので本文に残す。「どう動いたか」は ADR へ。**

- **記号（◎ / ○ / △）が変わった・(n/m) の読みが変わった・当初の想定が否定された・取り消された**
  → **ADR を 1 本起こし、更新ログに 1 行足す**
- **本文に取り消し線（`~~`）を残さない。** 取り消し線が出てきたら、それは ADR に行くもの
- **本文を削る前に ADR を書く。** 先に抜くと、抜いた瞬間に情報が消える

置き場所・ファイル名・連番の振り方・Status・本文からの参照の書き方は
[`docs/ADR/README.md`](../../../docs/ADR/README.md)、雛形は [`docs/ADR/_template.md`](../../../docs/ADR/_template.md)。

更新ログはマップの**末尾**に置き、**1 行に収める**。

```markdown
## 更新ログ

| 日付 | 動いたもの | ADR |
| --- | --- | --- |
| 2026-09-15 | 希望確認画面の未使用 (4/4) が崩れた | [入る側-0001](../ADR/user-journey-map/入る側-0001-希望確認画面の未使用が崩れた.md) |
```

**ここに理由を書き始めたら、それは ADR に書くもの。**

### 7. 改善機会リストを書き出す

**マップ 1 本ごとに**、そのファイルの末尾に改善機会を**箇条書き**で抽出する。

**ここが空だと後工程（HMW）が止まる。** 必ず埋める。

**統合したリストは別ファイルにしない。** HMW は `docs/journey/` にある**全マップの改善機会リストを
1 つの候補プール**として見て、そこから 1 つ選ぶ。まとめ直したファイルを作ると原本が二重化して、
どちらが最新か分からなくなる。

#### 1 項目は 4 行

```
N. <機会（解決策ではなく機会）> ◎ (n/m)
   根拠: <誰の何の証言か 1 行。人番号は書かない>
   効く先: ACTION <番号> / <他マップの改善機会 番号>
   注意: <項目に付く一般化の限界。無ければ書かない>
```

**項目に書くのはこの 4 種類だけ。** 残りは全部よそに持ち主がいる。

| 中身 | 行き先 |
| --- | --- |
| 機会そのもの ＋ 根拠 (n/m) | **項目に残す**（1 行目） |
| 効く先 | **項目に残す**（`効く先:`） |
| 項目に付く一般化の限界 | **項目に残す**（`注意:`） |
| **誰の何の証言か（逐語）** | `docs/interviews/` — **1 行に要約して消す**（手順 6） |
| **判定が動いた経緯** | **`docs/ADR/`**（手順 6.5） |
| **競合する読み・仮説** | **「仮説の判定」節** |
| **打ち手・解決策** | **書かない。HMW の仕事** |

#### 1 項目に (n/m) は 1 つ

**(n/m) が 2 つ以上ある項目は、機会が 2 つ以上入っている。分ける。**
逐語を消しても、複数の発見が 1 番に同居している限り 4 行にはならない
（これが肥大の最大要因である）。

分けるときは**元の番号に残すものを 1 つ決め、残りは末尾に新番号で足す**。

**行数の上限は設けない。** 完了チェックは grep 1 本 —
**1 項目の中に `(n/m)` が 2 つ以上無いか**。

#### 番号は追加順・欠番を詰めない

番号は本文内からも他マップからも参照される。
**項目が「否定・縮小」へ落ちたときに番号を詰めると、参照が黙って別項目を指す。**

- **既存の番号を動かさない**
- **欠番のまま空ける。詰めない**（「動かさない」だけだと、詰める操作が許されてしまう）

#### 3 節は同じフォーマットにしない

`確定 ◎ / 否定・縮小 / 未検証 △` を分ける理由は**確信度の言い直しではない**
（記号は 1 行目の (n/m) にすでに付いている）。**節ごとに次工程が違う**からである。

| 節 | 読み手 | 各項目が答えること | 形 |
| --- | --- | --- | --- |
| **確定 ◎** | **HMW** | 解きにいく候補 | 上の 4 行 |
| **否定・縮小** | **HMW** | **解きにいかない**もの（禁止リスト） | **1 行 ＋ 根拠記号** |
| **未検証 △** | **`interview-questions`** | **次にどうすれば埋まるか** | 機会 ＋ 記号 ＋ **どうすれば埋まるか**（相手・属性 ／ 記録） |

→ **HMW の候補プールは「確定」だけではなく「確定 ＋ 否定・縮小」である。** 片方は禁止リストとして働く。

**「否定・縮小」に `| 当初の想定 | 実態 |` の表を作らない。**
左列はまるごと**経緯**で、ADR の「それまでの結論」と同じものである
（→ 手順 6.5）。仮説の形をしている行は「仮説の判定」節へ。

#### 「N 人目」を書かない

**改善機会リストと 4 列の表から「N 人目」という語が 1 つも出ないのが正しい状態。**
`注意:` に「N 人目」が出てきたら、それは**人に付く上限**で、
**証言者表の `一般化の上限` 列の言い直し**である（→ 手順 6）。

#### interviews 側から番号で逆引きできるようにする

セルから「m 人のうちどの n 人か」が消えるので、**マップだけでは (n/m) を検算できなくなる**。
→ `docs/interviews/<連番>-<立場>.md` の「回答を並べる」表の **`論点` 列に、対応する
ACTION / 改善機会番号を併記する**（`interview-questions` skill 側。**1 列で、人が増えても増えない**）。

**これが無いと、手順 6 と 7 は検算できない (n/m) を量産するだけになる。**
